# 세입세잎 코드·아키텍처 감사 기록

- 감사일: 2026-08-20
- 대상: 현재 HEAD (`feature/AIGlass`)
- 방식: 공격적 코드 리뷰 및 총괄 기획 관점의 교차 검토, 빌드·정적 계약·테스트 결과 확인
- 범위: 이 문서는 2026-08-20 감사 결과의 1번부터 10번까지를 빠짐없이 보존한다. 코드와 Task 완료 상태를 이 문서 작성으로 변경하지 않는다.

## 1. Android 기능 회귀와 잘못된 완료 기록

현재 `android/settings.gradle.kts`는 `:app`만 포함한다. 과거의 `:core`, `:feature:property`, 검사·JPEG 업로드 모듈은 현재 빌드 대상이 아니다.

그러나 `공용 Task.md`에는 CRUD, 24개 테스트, 기기/API 검증이 완료됐다고 기록돼 있다. 이 기록은 과거 커밋의 증거이지 현재 HEAD의 증거가 아니다.

과거 Android 기능 커밋 `6d4982f`(inspection/OpenAPI), `1e4ae88`(JPEG/media), `149347e`(glass adapter)는 Git의 reachable history에는 남아 있다. 다만 현재 실행 트리에는 해당 기능 모듈이 포함되어 있지 않다.

### 조치

- 현재 디자인은 유지한다.
- 과거의 도메인·네트워크·미디어 기능만 현재 디자인 아래에 선택적으로 포팅한다.
- 현재 HEAD에서 다시 구현·실행·검증하기 전까지 Task 완료 상태를 재분류한다.

## 2. 프리뷰를 촬영·AI 분석 완료처럼 보여줌

`GlassConnectionViewModel.kt`의 DAT 흐름은 카메라 스트림 프리뷰만 수행한다. 실제 영상 저장, JPEG 추출, 서버 업로드는 존재하지 않는다.

반면 `AppNavGraph.kt`는 8초 타이머 뒤 분석 완료 화면으로 전환하며, `InspectionScreens.kt`는 고정 74%와 하드코딩된 분석 결과를 표시한다.

이 흐름은 사용자에게 실제 AI 결과 또는 실제 촬영 결과로 오인될 수 있다.

### 조치

- 현재 결과 화면을 `샘플 데이터`로 명확하게 격리하거나 운영 흐름에서 숨긴다.
- `테스트 영상 → JPEG 1장 → 등록 → PUT → complete`의 최소 세로 단면부터 실제로 연결한다.
- 서버와 Worker 결과가 없으면 `AI 분석 완료`를 표시하지 않는다.

## 3. 리포트가 서비스 불변 규칙 위반

`ReportScreens.kt`는 `직접 확인 24/28`, `확인 후 계약을 추천해요`와 같은 문구를 표시한다.

이는 다음 서비스 규칙에 어긋난다.

- AI는 하자 또는 안전 상태를 확정하지 않는다.
- MVP 현장 점검에는 체크리스트 상태 입력을 사용하지 않는다.
- AI는 계약 추천을 하지 않는다.
- 현재 공통 계약에는 최종 리포트 API가 없다.

### 조치

- 계약 추천, 등급, 체크리스트 완료율을 운영 흐름에서 제거한다.
- `확인 필요 관찰 결과`와 근거 JPEG만 표시한다.
- 사용자 검토 상태는 Android 앱의 사용자 행동으로 `ACTIVE → VIEWED` 또는 `ACTIVE → DISMISSED`만 변경한다.

## 4. 인증 계약과 서버 구현이 불일치

OpenAPI는 Bearer 인증을 요구하지만, `DemoUserContext.kt`는 모든 요청을 동일한 고정 사용자로 처리한다. 서버에도 Spring Security 구성이 없다. Android의 로그인 화면은 실제 인증이 아니라 화면 이동 수준이다.

이 상태에서 서버가 외부에 노출되면 모든 호출자가 동일 소유자의 데이터에 접근하게 된다.

### 조치

- 데모 단계에서도 Bearer 토큰을 principal 및 사용자 소유권과 연결한다.
- 인증이 구현되기 전까지 서버를 localhost에만 제한한다.
- 인증 없음의 401 응답과 타 사용자 데이터 접근 거부 테스트를 추가한다.

## 5. JPEG 증거를 완료 후에도 덮어쓸 수 있음

`MediaService.kt`는 최종 객체 키에 바로 presigned PUT URL을 발급한다. 완료 검증 후에도 URL 유효시간 동안 동일 키를 덮어쓸 수 있다.

그 결과 DB에 기록된 크기·메타데이터·분석 근거와 실제 증거 JPEG가 달라질 수 있다.

### 조치

- 업로드 시도별 임시 객체 키를 사용한다.
- 검증 성공 후 서버가 불변 최종 키로 객체를 승격하거나 복사한다.
- checksum 또는 object versionId를 저장한다.
- 완료된 증거 객체는 교체할 수 없게 처리한다.

## 6. 멱등성과 동시성 처리가 안전하지 않음

동일한 idempotency key 재요청이 최초 응답을 그대로 재생하지 않고 attempt와 URL을 다시 만들 수 있다. 생성 요청 재시도도 aggregate 상태를 변경할 위험이 있다. 동시에 `complete`와 `retry`가 수행되면 마지막 저장이 올바른 상태를 덮어쓸 수 있다.

동일 idempotency key의 동시 첫 요청은 unique 제약 충돌 뒤 일반 500으로 처리될 가능성도 있다.

### 조치

- idempotency key와 최초 응답·부수효과를 원자적으로 저장하고 이후 요청에는 그대로 재생한다.
- DB unique 충돌을 일반 500으로 보내지 않는다.
- `@Version`, pessimistic lock 또는 조건부 상태 전이를 적용한다.
- 같은 key 재시도, 동시 create, 동시 complete/retry를 검증하는 테스트를 추가한다.

## 7. AI Worker가 실질적으로 없음

`server/ai-worker`에는 README 수준의 내용만 있고 실행 코드·빌드·테스트가 없다. API는 미디어를 `QUEUED` 상태로 만들 수 있지만 실제 작업 발행이나 소비가 없어 영구 대기 상태가 될 수 있다.

Observation API와 Report API도 현재 OpenAPI 계약에 구현되어 있지 않다.

### 조치

첫 구현은 Redis 같은 추가 인프라보다 결정적인 Fake Worker가 적합하다.

```text
QUEUED → ANALYZING → COMPLETED
                    └─ evidenceMediaId를 가진 ACTIVE 관찰 생성
```

- 실제 모델 학습, STT, TTS는 이 단계에서 구현하지 않는다.
- AI는 확정 판정이 아니라 근거 미디어가 있는 `확인 필요 관찰`만 만든다.
- 관찰의 `VIEWED`, `DISMISSED` 변경은 Android 사용자 행동만으로 수행한다.

## 8. 공통 계약이 서로 충돌함

OpenAPI는 업로드 요청의 `zone`을 필수로 요구하지만, 도메인 문서는 구역을 AI 분류 결과로 정의한다. Android 입력값과 AI 출력값의 책임이 충돌한다.

또한 미디어 세트가 모두 업로드됐다는 것을 확정하는 finalize API가 없다. 따라서 마지막 이미지인지, 검사 aggregate를 언제 terminal 상태로 바꿔도 되는지 안정적으로 판단할 수 없다.

서버의 첫 데모 순서 문서는 이미지를 업로드한 뒤 inspection을 종료하도록 적고 있지만, 현재 서버는 `ENDED` 상태에서만 업로드를 허용한다. 실행 순서도 모순된다.

### 권장 계약

- Android 입력: 선택적인 `captureZoneHint`
- AI 출력: 확정이 아닌 `zone`, `zoneConfidence`
- 별도 media-set finalize 호출 뒤에만 inspection aggregate를 terminal 상태로 변경
- 데모 표준 순서: `start → capture → end → upload → finalize → analyze`

## 9. DAT 연결 복구와 생명주기가 취약함

현재 DAT 구현에는 다음 위험이 있다.

- 화면 이탈 또는 백그라운드 전환 시 stream 종료가 보장되지 않는다.
- 빠른 중복 시작으로 세션이나 카메라가 여러 개 생성될 가능성이 있다.
- 이전 error collector가 남을 가능성이 있다.
- 초기화 실패 및 `STOPPED` 이후 자동 재초기화·재연결이 없다.
- 현재 debug merged manifest에서 Meta 자격값이 `0`으로 병합되어 있다.

사용자가 제공한 logcat에서 실제 연결 실패 신호는 Google Play Services의 `ManagedChannel shutdown` 경고보다 다음 Meta Stella 로그다.

```text
Skipping openChannel serviceID=11014 after 5 consecutive failures
AidlDeviceConnectionAdapter: openChannel returned null
```

이 로그만으로 앱 코드가 최초 원인이라고 단정할 수는 없다. 다만 현재 앱은 이 상황에서 자동 복구가 약해 연결 끊김을 더 오래 지속시킬 수 있다.

### 조치

- 화면 lifecycle에 맞춰 preview stream, collector, camera를 확실히 해제한다.
- 시작/중지 전이 중복을 막는 단일 상태 전이를 둔다.
- 초기화 실패와 STOPPED에 대한 제한된 재시도 및 재연결 흐름을 추가한다.
- Meta 자격값이 없는 빌드에서는 fail-fast 설정 오류 UI를 표시한다. 실제 키는 Git에 기록하지 않는다.

## 10. 개발 인프라와 관측성

`server/infra/docker/compose.yml`은 PostgreSQL과 MinIO 포트를 모든 인터페이스에 노출하고 기본 자격값을 사용한다.

또한 `ApiExceptionHandler.kt`는 traceId를 응답에 만들지만 실제 예외와 연결해 로그로 남기지 않는다. 운영 중 사용자가 전달한 traceId로 서버 오류를 찾기 어렵다.

추가로 presigned 업로드는 API 단계에서 선언된 최대 크기만 확인한다. 실제 객체 업로드는 complete 전까지 임의 데이터가 저장될 수 있어, 인증이 없는 상태와 결합되면 저장소 남용 위험이 있다.

### 조치

- 로컬 개발 포트는 `127.0.0.1`에만 bind한다.
- 로컬 외 환경에서는 기본 비밀번호 사용을 거부한다.
- request traceId를 MDC와 예외 로그에 연결하고 민감 정보는 마스킹한다.
- 임시 업로드 객체의 크기·Content-Type을 complete 단계에서 검증하고, 만료된 임시 객체를 정리한다.
