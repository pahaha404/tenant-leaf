# 분석 완료 사진 기반 리포트 생성 기획서

## 1. 목적

Android가 업로드한 JPEG의 분석이 끝나면 서버가 결과를 `확인 필요 관찰`로 정리하고, 사용자가 별도의 생성 버튼을 누르지 않아도 임장 리포트를 자동 생성한다.

리포트는 다음 정보를 제공한다.

- 점검 날짜와 매물 이름
- 분석 성공·실패 사진 수
- 구역별 확인 필요 관찰
- 관찰 유형과 사용자 표시용 신뢰도
- 관찰마다 연결된 근거 JPEG와 AI 표시 영역
- 원본 JPEG 위에 정확히 겹쳐 표시되는 bbox, 한글 표시명과 신뢰도
- 관찰 수를 기반으로 계산한 참고 점수
- 분석 중·완료·빈 결과·부분 완료·실패 상태

AI 결과는 실제 하자, 안전 상태 또는 계약 가능 여부를 확정하지 않는다. 모든 결과는 사용자가 사진 근거를 보고 직접 확인하기 위한 보조 정보다.

bbox 저장·응답·Android 렌더링 규칙은 `ai/ai-video-defect/BBOX_RENDERING_ANDROID_BACKEND_GUIDE.md`를 따른다. 리포트 구현에서 이 문서와 가이드가 충돌하면 원본 이미지 픽셀 기준 `xyxy` 좌표를 보존하는 가이드의 원칙을 적용하고, 공통 API 계약과 OpenAPI도 같은 변경에서 일치시킨다.

## 2. 현재 구현 상태

현재까지 확인된 기반은 다음과 같다.

- Android가 원본 영상에서 고정 3초 구간마다 JPEG를 추출한다.
- Android가 JPEG를 객체 저장소에 업로드하고 미디어 완료 API를 호출한다.
- 미디어 집합 확정 API와 `mediaFinalizedAt` 필드가 있다.
- `media_analysis_jobs`와 `media_analysis_detections` 테이블이 있다.
- AI Worker가 대기 중인 JPEG를 분석해 작업을 `COMPLETED` 또는 `FAILED`로 바꿀 수 있다.
- OpenAPI에 관찰 조회·상태 변경과 리포트 조회 계약이 있다.
- Android에 리포트 `Generating`, `Completed`, `Empty`, `Partial`, `Error`, `Evidence Viewer` UI가 있다.
- AI 결과에 원본 이미지 크기와 원본 픽셀 기준 `xyxy` bbox를 반환하는 가이드가 있다.

아직 구현해야 하는 부분은 다음과 같다.

- 원시 탐지를 사용자용 `Observation`으로 변환하는 서버 로직과 DB 테이블
- 관찰과 1~3장의 근거 미디어 연결
- 모든 분석의 종료 여부를 판단하는 리포트 생성 조정 로직
- 리포트 DB 테이블과 자동 생성 로직
- 리포트·관찰 Controller, Service, Repository
- 근거 사진 조회용 임시 서명 URL 발급
- 원본 픽셀 `xyxy` bbox와 이미지 크기를 보존하는 DB·OpenAPI 계약 정합화
- AI 입력과 Android 조회 이미지의 EXIF 방향·픽셀 일치 처리
- 구역별 결과 카드와 Evidence Viewer의 동적 bbox 오버레이
- Android 리포트 ViewModel·Repository와 실제 API 응답 연결

## 3. MVP 완료 흐름

```text
Android가 JPEG 업로드 완료
→ 서버가 media를 UPLOADED로 확정
→ 서버가 EXIF 방향을 정규화하고 AI·Android가 사용할 동일 JPEG를 확정
→ media_analysis_jobs를 QUEUED로 등록
→ Android가 미디어 집합 finalize 호출
→ AI Worker가 JPEG별 분석 수행
→ 원본 이미지 크기와 원시 픽셀 xyxy 결과를 media_analysis_detections에 저장
→ 서버가 임계값 이상 결과를 Observation으로 변환
→ 분석 작업을 COMPLETED 또는 FAILED로 종료
→ ReportGenerationCoordinator가 임장 전체 상태 재평가
→ 모든 사진 분석이 최종 상태이면 리포트 자동 생성
→ Android가 GET /inspections/{inspectionId}/report를 조회
→ 상태에 맞는 리포트 UI 표시
→ 사용자가 관찰을 선택해 근거 사진과 bbox 확인
```

리포트 생성용 `POST` API는 추가하지 않는다. 미디어 분석 종료를 서버가 감지하여 자동 생성한다.

## 4. 리포트 자동 생성 조건

다음 조건을 모두 만족해야 리포트 생성을 시작한다.

1. 임장 상태가 `ENDED`다.
2. `mediaFinalizedAt`이 존재한다.
3. 확정 요청의 `expectedMediaCount`와 임장에 등록된 미디어 수가 같다.
4. 확정된 모든 미디어가 업로드 완료 상태다.
5. 모든 미디어 분석 작업이 `COMPLETED` 또는 최종 `FAILED`다.
6. 아직 같은 임장의 리포트가 생성되지 않았거나 재평가가 필요한 상태다.

첫 번째 사진 분석이 끝났다는 이유만으로 리포트를 만들면 안 된다. 반드시 미디어 집합 확정 이후 전체 사진 수를 기준으로 판단한다.

생성 중 화면의 전체 사진 수는 `expectedMediaCount`에서 유래한 리포트 응답의 `totalMediaCount`를 사용한다. 처리 수는 `successfulMediaCount + failedMediaCount`이며, 아직 `QUEUED` 또는 `ANALYZING`인 사진도 전체 수에 포함한다. 따라서 확정된 JPEG가 21장이고 아직 완료된 분석이 없다면 `0 / 21장`으로 표시해야 하며 `0 / 0장`으로 표시해서는 안 된다.

### 결과 상태

| 조건 | ReportStatus | Android UI |
|---|---|---|
| 미디어 확정 후 분석 대기·분석 중 | `WAITING_FOR_ANALYSIS` | `Report / Detail / Generating` |
| 모든 분석 종료 후 리포트 조립 중 | `GENERATING` | `Report / Detail / Generating` |
| 성공 사진 1장 이상, 실패 0장, 관찰 1건 이상 | `COMPLETED` | `Report / Detail / Completed` |
| 성공 사진 1장 이상, 실패 0장, 관찰 0건 | `COMPLETED` | `Report / Detail / Empty` |
| 성공 사진 1장 이상, 일부 사진 최종 실패 | `PARTIAL_COMPLETED` | `Report / Detail / Partial` |
| 성공 사진 0장 | `FAILED` + `NO_ANALYZABLE_MEDIA` | `Report / Detail / Error` |
| 리포트 조립·저장 자체 실패 | `FAILED` + `GENERATION_FAILED` | `Report / Detail / Error` |

탐지가 0건이어도 사진 분석 자체가 성공했다면 `COMPLETED`다. 사용자 문구는 `하자 없음`이 아니라 다음 문장으로 고정한다.

> 현재 촬영 근거에서 확인 필요 관찰이 생성되지 않았습니다.

## 5. 원시 탐지에서 관찰 생성

### 5.1 변환 기준

- `classId`를 기준으로 13개 `ObservationType`에 1:1 변환한다.
- AI 라벨 문자열은 검증용으로만 사용하고 분기 기준으로 사용하지 않는다.
- 모델 버전과 classId별 `observationMinConfidence` 이상인 탐지만 관찰로 생성한다.
- 임계값 미만 원시 탐지는 `media_analysis_detections`에 보존하지만 사용자 리포트에는 노출하지 않는다.
- 구역 분류가 확실하면 AI 구역을 사용한다.
- 구역 분류가 불확실하거나 실패하면 `UNKNOWN`을 사용한다.
- 사용자가 구역을 보정한 경우 리포트에는 사용자 보정 구역을 우선 사용하고 AI 원본 구역은 보존한다.

### 5.2 반복 흔적

MVP 첫 구현에서는 인접 사진의 관찰을 자동으로 합치지 않는다. 시간과 라벨만 같은 서로 다른 흔적을 잘못 합치는 위험을 피하기 위해서다.

향후 다음 조건을 모두 검증할 수 있을 때만 병합한다.

- 같은 임장
- 같은 최종 구역
- 같은 `ObservationType`
- `sourceVideoOffsetMs` 차이가 6초 이내
- crop 이미지 유사도가 확정 기준 이상

병합할 때 근거 사진은 최대 3장으로 제한하고 신뢰도가 가장 높은 사진을 대표 근거로 지정한다.

### 5.3 관찰 문구

문구는 자유 생성 LLM 대신 버전이 있는 템플릿으로 만든다.

예시:

| ObservationType | 제목 예시 | 설명 예시 |
|---|---|---|
| `CRACK_CHECK_NEEDED` | 균열로 추정되는 흔적 | 표시된 벽면의 선형 흔적을 직접 확인해 주세요. |
| `MOLD_CHECK_NEEDED` | 곰팡이로 추정되는 흔적 | 습기나 변색이 있는지 표시된 부분을 직접 확인해 주세요. |
| `WATER_DAMAGE_CHECK_NEEDED` | 누수로 추정되는 흔적 | 물 번짐이나 변색 여부를 표시된 부분에서 확인해 주세요. |
| `OTHER_CHECK_NEEDED` | 종류를 분류하지 못한 확인 필요 흔적 | AI가 구체적인 유형을 분류하지 못한 흔적입니다. 사진을 직접 확인해 주세요. |

`확정`, `안전`, `계약 추천`, `문제없음` 같은 표현은 사용하지 않는다.

### 5.4 bbox 원본 좌표 계약

- AI가 본 정방향 전체 JPEG를 bbox의 기준 이미지로 삼는다. crop이나 썸네일을 기준 이미지로 사용하지 않는다.
- `image.width`, `image.height`는 EXIF 방향 정규화가 끝난 실제 픽셀 크기다.
- bbox는 왼쪽 위 원점의 원본 픽셀 기준 `xyxy`이며 `left`, `top`, `right`, `bottom`을 `DOUBLE PRECISION`으로 보존한다.
- 유효 범위는 `0 <= left < right <= image.width`, `0 <= top < bottom <= image.height`다.
- 백엔드는 좌표를 `0..1`로 정규화하거나 `xywh`로 변환하여 원본 값을 덮어쓰지 않는다.
- 필요하면 정규화 좌표를 파생 필드로 함께 제공할 수 있지만 원본 픽셀 좌표가 항상 기준값이다.
- AI 결과의 `classId`, 영문 `label`, `confidence`, 모델 버전과 원시 bbox를 함께 보존한다.

현재 공통 계약의 13개 `classId`와 영문 `label`을 서비스의 기준으로 사용한다. BBOX 가이드의 `water_damage`, `tile_crack`, `unknown_defect`처럼 밑줄 또는 과거 이름을 쓰는 결과는 Worker 입력 경계에서 최신 공통 라벨로 정규화한다. 구체적인 유형을 분류하지 못한 확인 필요 결과는 `classId=12`, `label=other`로 저장하고 사용자에게 `하자 의심` 또는 `기타 확인 필요`로 표시한다.

`displayLabel`과 `displayColor`는 사용자 표시 전용이다. 서버는 AI 값을 그대로 신뢰하지 않고 버전이 있는 13개 표시 매핑으로 검증하거나 보완한다. 박스 라벨은 `곰팡이 추정 흔적 · 76%`처럼 표시하고, 카드 제목은 `곰팡이로 추정되는 흔적 확인 필요`처럼 비확정 표현을 사용한다.

### 5.5 이미지 방향과 변형

서버는 분석 전에 다음 순서로 이미지를 정규화한다.

1. JPEG의 EXIF Orientation을 읽는다.
2. 픽셀을 실제 정방향으로 회전한다.
3. Orientation을 `1`로 바꾸거나 해당 메타데이터를 제거한다.
4. 같은 정규화 JPEG를 AI 입력과 Android 조회에 사용한다.
5. 정규화 후 `width`, `height`를 분석 기준 크기로 저장한다.

분석 후 crop·회전은 bbox 불일치 위험 때문에 MVP에서 하지 않는다. resize가 불가피하면 좌표 사본에 `scaleX`, `scaleY`를 적용하되 원시 좌표를 유지한다. 사용자에게 제공하는 `viewUrl`의 이미지 픽셀 방향과 비율은 AI 입력과 같아야 한다.

### 5.6 구역별 카드와 다중 bbox 표시

- 구역별 확인 결과 카드는 관찰 하나를 중심으로 구성하며 대표 근거 사진 위에 해당 관찰의 bbox를 강조한다.
- 같은 사진에 다른 관찰이 여러 개 있어도 카드에서는 선택한 관찰만 기본 표시하여 화면이 복잡해지지 않게 한다.
- Evidence Viewer에서는 선택한 bbox를 가장 위에 굵게 표시하고, `모든 관찰 표시` 기능을 제공할 경우 같은 `mediaId`의 임계값 이상 bbox를 함께 표시한다.
- 각 bbox는 `observationId` 또는 원시 `detectionId`와 연결해 사용자가 박스를 선택하면 유형·신뢰도·설명·검토 상태를 확인할 수 있게 한다.
- 겹치는 박스는 선택한 박스를 마지막에 그리며, 임계값 미만 결과는 사용자 화면에 표시하지 않는다.
- Android는 서버가 미리 그린 이미지에 의존하지 않고 `imageUrl + detections[]`를 사용해 동적으로 그린다. `annotatedImageUrl`은 디버깅·검증용 선택 필드일 뿐 리포트의 기준 데이터가 아니다.

## 6. DB 설계안

기존 테이블은 유지하고 새 Flyway 마이그레이션으로 추가한다. 실제 버전 번호는 병합 시점의 최신 마이그레이션 다음 번호를 사용한다.

### 6.1 observations

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID PK | 관찰 ID |
| `inspection_id` | UUID FK | 임장 ID |
| `type` | VARCHAR | `ObservationType` |
| `status` | VARCHAR | `ACTIVE`, `VIEWED`, `DISMISSED` |
| `ai_zone` | VARCHAR | AI 원본 구역 |
| `zone_confidence` | NUMERIC | AI 구역 신뢰도 |
| `zone_uncertain` | BOOLEAN | 구역 불확실 여부 |
| `zone_model_version` | VARCHAR | 구역 모델 버전 |
| `user_corrected_zone` | VARCHAR NULL | 사용자 보정 구역 |
| `class_id` | INTEGER | 원본 AI classId |
| `ai_label` | VARCHAR | 정규화된 원본 라벨 |
| `confidence` | NUMERIC | 원시 신뢰도 |
| `observation_min_confidence` | NUMERIC | 생성 당시 적용 임계값 |
| `model_version` | VARCHAR | 하자 모델 버전 |
| `template_version` | VARCHAR | 관찰 문구 템플릿 버전 |
| `created_at` | TIMESTAMPTZ | 생성 시각 |
| `updated_at` | TIMESTAMPTZ | 수정 시각 |

같은 원시 탐지가 재전송돼도 관찰이 중복 생성되지 않도록 탐지 ID 또는 `(mediaId, detectionId, templateVersion)` 기반 유일 제약을 둔다.

### 6.2 observation_evidence

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `observation_id` | UUID FK | 관찰 ID |
| `media_id` | UUID FK | 근거 JPEG ID |
| `detection_id` | UUID FK | 원시 탐지 ID |
| `is_representative` | BOOLEAN | 대표 근거 여부 |
| `coordinate_system` | VARCHAR | `PIXEL_XYXY` 고정 |
| `image_width` | INTEGER | AI 기준 정방향 이미지 너비 |
| `image_height` | INTEGER | AI 기준 정방향 이미지 높이 |
| `bbox_left` | DOUBLE PRECISION | 원본 픽셀 기준 왼쪽 x |
| `bbox_top` | DOUBLE PRECISION | 원본 픽셀 기준 위쪽 y |
| `bbox_right` | DOUBLE PRECISION | 원본 픽셀 기준 오른쪽 x |
| `bbox_bottom` | DOUBLE PRECISION | 원본 픽셀 기준 아래쪽 y |
| `confidence` | NUMERIC | 해당 근거 탐지 신뢰도 |
| `created_at` | TIMESTAMPTZ | 연결 시각 |

제약:

- 관찰 하나당 근거 1~3장
- 대표 근거 정확히 1장
- 같은 임장의 업로드 완료 JPEG만 연결
- 이미지 너비·높이는 양수이고 bbox 네 값은 음수가 아님
- 서비스 계층에서 `left < right <= image_width`, `top < bottom <= image_height` 검증
- `media_id`, 저장된 이미지 크기와 AI 입력 이미지가 일치하지 않으면 관찰 생성을 거부하고 분석 작업을 안전하게 실패 처리

### 6.3 reports

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID PK | 리포트 ID |
| `property_id` | UUID FK | 매물 ID |
| `inspection_id` | UUID FK UNIQUE | 임장당 리포트 1개 |
| `status` | VARCHAR | `ReportStatus` |
| `successful_media_count` | INTEGER | 분석 성공 사진 수 |
| `failed_media_count` | INTEGER | 최종 실패 사진 수 |
| `observation_count` | INTEGER | `DISMISSED` 제외 관찰 수 |
| `reference_score` | INTEGER NULL | 참고 점수, 실패 상태에는 NULL |
| `score_policy_version` | VARCHAR NULL | 점수 정책 버전 |
| `score_is_provisional` | BOOLEAN | 부분 완료의 잠정 점수 여부 |
| `failure_code` | VARCHAR NULL | 실패 코드 |
| `template_version` | VARCHAR | 리포트 문장 템플릿 버전 |
| `generated_at` | TIMESTAMPTZ NULL | 생성 완료 시각 |
| `created_at` | TIMESTAMPTZ | 최초 생성 시각 |
| `updated_at` | TIMESTAMPTZ | 갱신 시각 |

`inspection_id`에 유일 제약을 두어 Worker 중복 완료 이벤트나 서버 재시작 복구 작업이 동시에 실행돼도 리포트가 하나만 생성되게 한다.

리포트 본문을 긴 문자열 또는 JSON으로 중복 저장하지 않는다. 상세 조회 시 리포트 요약과 현재 `DISMISSED`가 아닌 관찰·근거를 조합한다. 문구는 저장된 템플릿 버전으로 재현한다.

## 7. 참고 점수 정책안

MVP 점수는 다음처럼 단순하게 계산한다.

```text
referenceScore = max(0, 100 - (리포트 포함 관찰 수 × 5))
```

규칙:

- `DISMISSED` 관찰은 점수 차감에서 제외한다.
- `COMPLETED`이며 관찰 0건이면 100점으로 표시할 수 있지만 `하자 없음` 또는 `안전 점수`로 표현하지 않는다.
- `PARTIAL_COMPLETED`는 분석 실패 사진이 있으므로 `잠정 참고 점수`로 표시한다.
- `FAILED`에는 점수를 표시하지 않는다.
- 같은 흔적 자동 병합 전에는 반복 촬영된 흔적이 여러 관찰로 계산될 수 있음을 안내한다.
- 점수는 계약·안전·주거 품질을 평가하는 절대 지표가 아니다.

현재 OpenAPI `ReportSummary`에는 점수 필드가 없다. 구현 전 다음 필드를 공통 API 계약과 OpenAPI에 함께 추가한다.

- `referenceScore`: 0~100, nullable
- `scorePolicyVersion`: 문자열, nullable
- `scoreIsProvisional`: boolean

점수 정책을 확정하지 못하면 서버와 Android에서 임의 계산하지 않고 첫 구현에서 점수 표시를 숨긴다.

## 8. 리포트 생성 서비스 설계

### 8.1 주요 구성요소

- `ObservationProjectionService`: 원시 탐지를 관찰과 근거로 변환
- `ReportGenerationCoordinator`: 임장 전체의 생성 가능 여부 판단
- `ReportService`: 리포트 상태 생성·갱신·상세 조회
- `ReportRepository`: 임장당 리포트 유일성 및 잠금 처리
- `ObservationRepository`: 관찰 목록·상세·상태 변경
- `EvidenceViewUrlService`: 권한 확인 후 근거 사진 임시 조회 URL 발급
- `ReportTemplateRenderer`: 버전별 사용자 문구 생성

### 8.2 트리거

다음 시점마다 `ReportGenerationCoordinator.evaluate(inspectionId)`를 호출한다.

1. 미디어 집합 finalize 성공 직후
2. 개별 분석 작업이 `COMPLETED` 또는 최종 `FAILED`로 전환된 직후
3. 서버 재시작 후 미완료 리포트 복구 스캔

분석 Worker가 Spring Boot 내부 서비스를 직접 호출하도록 결합하지 않는다. Worker 결과 저장 경계에서 임장 ID를 확인한 뒤 조정 서비스를 호출하거나, 트랜잭션 완료 이벤트를 발행한다.

### 8.3 동시성·멱등성

- 임장 ID별 DB 잠금 또는 원자적 upsert를 사용한다.
- `reports.inspection_id` 유일 제약을 둔다.
- 이미 최종 상태인 리포트에 같은 완료 이벤트가 와도 중복 생성하지 않는다.
- 생성 중 서버가 종료돼도 복구 스캔이 `GENERATING` 또는 `WAITING_FOR_ANALYSIS` 리포트를 다시 평가한다.
- 관찰 생성은 원시 탐지 식별자를 기준으로 멱등 처리한다.

## 9. API 응답과 Android 연결

### 9.0 공간별 대표 사진

- `representativePhotos`는 `mediaId`, `zone`, `zoneUncertain`, `zoneModelVersion`, `sourceVideoOffsetMs`, 이미지 크기와 만료형 조회 URL을 포함한다.
- Gemini의 `kitchen`, `living_room`, `bathroom`, `unknown`은 각각 `KITCHEN`, `LIVING_ROOM`, `BATHROOM`, `UNKNOWN`으로 정규화한다.
- Android 품질 선별을 통과한 분석 완료 JPEG 중 같은 공간에서 6초 이상 떨어진 사진을 공간별 최대 3장, 전체 최대 12장 선택한다.
- 확실한 구역은 `주방 대표 사진`, `거실·방 대표 사진`, `화장실 대표 사진`으로 표시하고 불확실·미지원 결과는 `공간 확인 필요`로 표시한다.
- 대표 사진의 공간 분류는 하자 관찰의 공간 확정과 분리한다. 확인 필요 관찰 목록은 계속 촬영 순서로 표시한다.

기존 외부 API를 사용한다.

```http
GET /api/v1/properties/{propertyId}/reports
GET /api/v1/inspections/{inspectionId}/report
GET /api/v1/inspections/{inspectionId}/observations
GET /api/v1/observations/{observationId}
PATCH /api/v1/observations/{observationId}/status
```

리포트 생성용 `POST`는 만들지 않는다.

### 9.1 OpenAPI 보완 제안

현재 Android 화면을 추가 API 호출 없이 채우려면 `ReportDetail` 또는 `ReportSummary`에 다음 표시 필드가 필요하다.

- `propertyDisplayName`: 사용자가 등록한 매물 이름
- `inspectionEndedAt`: 점검 종료 날짜·시각
- `referenceScore`
- `scorePolicyVersion`
- `scoreIsProvisional`

근거 미디어 계약에는 다음 필드가 필요하다.

- `coordinateSystem`: `PIXEL_XYXY`
- `image`: `width`, `height`
- `box`: `left`, `top`, `right`, `bottom`
- `classId`, `label`, `displayLabel`, `displayColor`, `confidence`
- 같은 사진의 여러 박스를 표시할 때 사용할 `detections[]`

매물 이름은 별도 매물 API를 호출해 조합할 수도 있지만 리포트 목록과 상세에서 N+1 요청이 생기므로 리포트 조회 응답에 읽기 전용 표시값을 포함하는 편을 추천한다.

계약 필드를 변경할 때는 `도메인 규칙.md`, `team/00_shared/공통 api 계약.md`, `server/shared-types/openapi/openapi.yaml`, 서버 구현과 Android 매핑을 같은 변경에서 수정한다.

### 9.2 Evidence Viewer

근거 사진 응답에는 다음을 제공한다.

- `mediaId`
- `viewUrl`
- `viewUrlExpiresAt`
- `image.width`, `image.height`
- `coordinateSystem=PIXEL_XYXY`
- `detections[].observationId` 또는 추적 가능한 탐지 식별자
- `detections[].classId`, `label`, `displayLabel`, `displayColor`, `confidence`
- `detections[].box.left/top/right/bottom`
- 대표 근거 여부

서버 내부 MinIO 객체 키나 로컬 경로는 노출하지 않는다. `viewUrl`은 요청 사용자의 매물·임장 소유권 확인 후 짧은 유효기간의 GET 서명 URL로 발급한다. Android는 만료 또는 403 응답을 받으면 관찰 상세를 다시 조회해 새 URL을 받는다.

응답 예시는 다음과 같다.

```json
{
  "mediaId": "4ae76a4f-4dd9-4380-949a-8d80b47dfaa2",
  "viewUrl": "https://example.invalid/signed-evidence-url",
  "viewUrlExpiresAt": "2026-08-24T12:15:00+09:00",
  "image": {
    "width": 1920,
    "height": 1080
  },
  "coordinateSystem": "PIXEL_XYXY",
  "detections": [
    {
      "observationId": "4f8bfe16-f3cd-44d8-ae6c-7d4caac20a51",
      "classId": 3,
      "label": "waterdamage",
      "displayLabel": "누수",
      "displayColor": "#1E88E5",
      "confidence": 0.87,
      "box": {
        "left": 120.5,
        "top": 80.2,
        "right": 640.8,
        "bottom": 410.4
      }
    }
  ]
}
```

`annotatedImageUrl`을 선택적으로 반환할 수 있지만 결과 검수나 관리자 확인용으로 제한한다. 사용자가 박스를 선택·숨김·확대할 수 있어야 하므로 실제 앱은 원본 이미지와 구조화된 bbox를 사용한다.

### 9.3 Android 상태 매핑

```text
NOT_REQUESTED          → 리포트 없음 안내
WAITING_FOR_ANALYSIS   → ReportSamples.GENERATING 형태
GENERATING             → ReportSamples.GENERATING 형태
COMPLETED + 관찰 있음   → Completed
COMPLETED + 관찰 0건    → Empty
PARTIAL_COMPLETED      → Partial
FAILED                 → Error
관찰 근거 선택          → Evidence Viewer
```

현재 Android의 예시 `ReportSamples`는 실제 API DTO를 `ReportDetailUiModel`로 바꾸는 Mapper와 ViewModel로 교체한다. 8초 타이머 기반 `reportProcessing`은 데모 fallback으로만 남기고, 실제 상태 판단에는 서버 응답을 사용한다.

### 9.4 Android bbox 렌더링

MVP는 이미지 전체를 보존하는 `ContentScale.Fit`을 사용한다. 이미지와 `Canvas`는 padding을 제외한 동일한 크기의 컨테이너에 겹쳐 배치한다.

```text
scale = min(viewWidth / imageWidth, viewHeight / imageHeight)
drawnWidth = imageWidth * scale
drawnHeight = imageHeight * scale
offsetX = (viewWidth - drawnWidth) / 2
offsetY = (viewHeight - drawnHeight) / 2

screenLeft = offsetX + left * scale
screenTop = offsetY + top * scale
screenRight = offsetX + right * scale
screenBottom = offsetY + bottom * scale
```

- 계산은 `Float`로 수행하고 상태바·툴바 위치를 이미지 내부 좌표에 섞지 않는다.
- `displayColor`로 박스와 라벨 배경을 그리고 `displayLabel`과 반올림한 신뢰도를 표시한다.
- 선택한 박스는 굵은 선과 높은 z-order로 강조한다.
- 확대·이동을 지원하면 이미지와 Canvas에 같은 변환 행렬을 적용한다.
- API의 이미지 크기와 실제 내려받은 JPEG 크기가 다르면 잘못된 박스를 그리지 말고 오류·재조회 상태를 표시한다.

## 10. 조회 정렬과 표시 규칙

- 매물 리포트 목록은 `generatedAt` 또는 `createdAt` 최신순이다.
- 리포트 관찰은 최종 구역 순서, 대표 근거의 `sourceVideoOffsetMs`, 신뢰도 내림차순으로 정렬한다.
- 권장 구역 순서는 `KITCHEN`, `LIVING_ROOM`, `BATHROOM`, `UNKNOWN`이다. 현관과 창틀은 AI 구역 분류 범위에서 제외하며 관련 사진은 `UNKNOWN(구역 확인 필요)`로 표시한다.
- `DISMISSED` 관찰은 기본 리포트 응답과 관찰 수·참고 점수에서 제외한다.
- `VIEWED`와 `ACTIVE`는 리포트에 포함하되 검토 상태를 함께 반환한다.
- 사진 삭제 또는 보관 만료로 근거를 열 수 없으면 관찰은 유지하고 `근거 사진 사용 불가` 상태를 제공한다.

## 11. 오류 처리

최소 오류 상황:

- 임장이 `ENDED`가 아님
- 미디어 집합 미확정
- 예상 사진 수 불일치
- 업로드 미완료 사진 존재
- 분석 작업 누락 또는 영구 실패
- 원시 결과의 classId-label 불일치
- bbox 범위 오류
- AI 기준 이미지 크기와 조회 JPEG 크기 불일치
- EXIF 방향 정규화 실패
- bbox 표시 필드 또는 색상 형식 오류
- 다른 사용자의 매물·임장·미디어 접근
- MinIO 근거 사진 조회 실패
- 리포트 생성 중 서버 재시작

외부 응답에는 내부 객체 키, SQL 메시지, 모델 파일 경로와 스택 트레이스를 포함하지 않는다. 서버 로그에도 서명 URL 전체를 기록하지 않는다.

- 원본 픽셀 bbox 범위와 이미지 크기 검증
- `classId`별 표시 라벨·색상 매핑

### 저장소·통합 테스트

- 임장당 리포트 1개 유일성
- 동시 분석 완료 이벤트의 중복 생성 방지
- 서버 재시작 후 `GENERATING` 복구
- 같은 탐지 결과 재전송 시 관찰 중복 방지
- 관찰당 근거 1~3장과 대표 근거 1장 제약
- 다른 사용자 리포트·관찰·근거 조회 차단
- MinIO GET 서명 URL 발급과 만료 후 재발급
- 부분 실패와 전체 실패 상태
- AI 입력과 Android 조회 이미지의 크기·방향 일치
- 동일 미디어 다중 탐지 응답과 선택 관찰 연결

### E2E 테스트

1. 임장을 `ENDED`로 종료한다.
2. 실제 Android 생성 JPEG 21장을 업로드한다.
3. 미디어 집합을 `expectedMediaCount=21`로 확정한다.
4. AI Worker가 21장을 처리한다.
5. DB에서 모든 작업이 최종 상태인지 확인한다.
6. 리포트가 자동으로 하나만 생성되는지 확인한다.
7. Android에서 날짜·매물명·상태·관찰·점수를 확인한다.
8. 관찰을 눌러 실제 MinIO 근거 사진과 bbox를 확인한다.
9. 카드에서는 선택 관찰만, Evidence Viewer에서는 선택 박스와 같은 사진의 전체 관찰을 확인한다.
10. 가로·세로·EXIF 회전 사진과 Fit 여백에서도 박스가 같은 위치인지 확인한다.
11. 관찰을 `DISMISSED` 후 복원하고 리포트 반영을 확인한다.
12. 앱·서버를 재시작해도 같은 리포트가 유지되는지 확인한다.

## 14. 완료 기준

- [ ] 분석이 모두 끝난 임장에 리포트가 자동으로 정확히 하나 생성된다.
- [ ] 성공·빈 결과·부분 완료·전체 실패가 계약대로 구분된다.
- [ ] 13개 AI classId가 올바른 `ObservationType`으로 변환된다.
- [ ] 임계값 미만 원시 탐지가 리포트에 노출되지 않는다.
- [ ] 모든 사용자 관찰 문장이 1~3장의 근거 `mediaId`로 추적된다.
- [ ] Android에서 실제 날짜·매물명·관찰·사진·bbox를 확인할 수 있다.
- [ ] AI가 본 정방향 JPEG와 Android가 보는 JPEG의 픽셀 크기·비율·방향이 같다.
- [ ] 원본 픽셀 `xyxy` bbox가 세로·가로·Fit 여백·확대 상태에서도 정확한 위치에 표시된다.
- [ ] 선택 관찰 강조, 다중 bbox, 한글 표시명·색상·신뢰도가 계약과 일치한다.
- [ ] `DISMISSED` 관찰이 기본 리포트와 참고 점수에서 제외되고 복원된다.
- [ ] 다른 사용자의 리포트와 근거 사진 접근이 차단된다.
- [ ] 중복 이벤트와 서버 재시작에도 중복 리포트가 생기지 않는다.
- [ ] 서버 단위·통합 테스트와 Android 단위·빌드 테스트가 통과한다.
- [ ] 실제 기기에서 JPEG 업로드부터 리포트 열람까지 연속 시나리오를 검증한다.
