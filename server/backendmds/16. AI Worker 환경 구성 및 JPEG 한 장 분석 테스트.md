# AI Worker 환경 구성 및 JPEG 한 장 분석 테스트 요청

## 1. 목적

`15. 사진 분석 처리 요청.md`에서 구현한 비동기 JPEG 분석 파이프라인을 로컬 환경에서 실제로 검증한다.

이번 작업은 Android가 추출·업로드한 JPEG 가운데 PostgreSQL에서 `QUEUED` 상태인 작업 **한 건만** 처리해 다음 흐름이 이어지는지 확인하는 데 목적이 있다.

```text
UPLOADED JPEG
→ media_analysis_jobs.QUEUED
→ AI Worker가 작업 선점
→ MinIO JPEG 다운로드
→ Binary YOLO + Multiclass YOLO 추론
→ ANALYZING
→ 탐지 결과·모델 버전 저장
→ COMPLETED 또는 FAILED
```

탐지 결과가 0건이어도 모델 실행과 결과 저장이 정상적으로 끝났다면 `COMPLETED`다. 이를 `하자 없음` 또는 `안전함`으로 해석하지 않는다.

## 2. 작업 범위

포함:

- Python 3.14 가상환경 구성
- `server/ai-worker/requirements.txt` 설치
- Binary·Multiclass `best.pt` 경로와 모델 로딩 검증
- PostgreSQL·MinIO·Spring Boot 연결 확인
- 대기 중인 JPEG 분석 작업 한 건 확인
- Worker `--once` 실행
- 작업·미디어·임장 상태와 탐지 결과 저장 확인
- 탐지 결과가 있을 때 비공개 crop 객체 저장 확인

제외:

- 원본 영상 서버 업로드 또는 영상 직접 분석
- 대기 작업 전체의 연속 처리
- 실패 작업 자동 재시도·백오프 정책 확정
- 원시 탐지를 외부 `Observation`으로 변환하는 API
- 관찰 병합, 리포트 생성과 Android 결과 UI 연결
- 모델 정확도·threshold·처리 성능 최적화

## 3. 사전 안전 규칙

- 실제 `.env`, 비밀번호, DB 연결 문자열과 MinIO 키를 Git에 추가하지 않는다.
- `*.pt`, 원본 JPEG, crop과 임시 분석 결과를 Git에 추가하지 않는다.
- 모델 가중치를 일반 GitHub나 공개 링크로 공유하지 않는다.
- 내부 객체 키, 서명 URL, 로컬 경로와 촬영 사진을 로그·문서·PR에 남기지 않는다.
- 전체 서버 통합 테스트로 로컬 사용 데이터를 삭제하지 않는다.
- 한 장 테스트가 성공하기 전에는 Worker를 무한 대기 모드로 실행하지 않는다.
- `--once`가 선점한 작업은 실패해도 `FAILED`로 종결된다. 실패 행을 SQL로 임의 수정하지 말고 원인을 기록한 뒤 재시도 계약에 따라 처리한다.

## 10. 분석할 대기 작업 한 건 확인

Worker 실행 전에 DBeaver에서 가장 오래된 분석 가능 작업을 확인한다.

```sql
SELECT
    j.id AS job_id,
    j.media_id,
    j.status AS job_status,
    j.attempt_count,
    m.upload_status,
    m.analysis_status,
    m.width,
    m.height,
    j.created_at
FROM media_analysis_jobs j
JOIN media m ON m.id = j.media_id
WHERE j.status = 'QUEUED'
  AND j.available_at <= NOW()
  AND m.upload_status = 'UPLOADED'
  AND m.deleted_at IS NULL
ORDER BY j.created_at
LIMIT 1;
```

실행 전 `job_id`와 `media_id`를 로컬 테스트 기록에만 적어 둔다. 조회 결과가 없다면 Worker를 실행하지 말고 Android 업로드 완료 API가 분석 작업을 생성했는지 먼저 점검한다.

## 12. 분석 결과 확인

### 12.1 작업 상태

실행 전에 기록한 `job_id`로 확인한다.

```sql
SELECT
    id,
    media_id,
    status,
    attempt_count,
    model_version,
    failure_code,
    failure_message,
    started_at,
    completed_at
FROM media_analysis_jobs
WHERE id = '<확인한 job_id>';
```

성공 기준:

- `status = 'COMPLETED'`
- `attempt_count = 1`
- `model_version`이 비어 있지 않음
- `started_at`, `completed_at`이 기록됨
- `failure_code`, `failure_message`가 `NULL`

### 12.2 미디어와 임장 집계 상태

```sql
SELECT id, upload_status, analysis_status, uploaded_at, updated_at
FROM media
WHERE id = '<확인한 media_id>';

SELECT i.id, i.status, i.analysis_status, i.updated_at
FROM inspections i
JOIN media m ON m.inspection_id = i.id
WHERE m.id = '<확인한 media_id>';
```

해당 미디어는 `analysis_status='COMPLETED'`여야 한다. 임장 전체 상태는 다른 JPEG 작업 상태까지 포함해 서버가 계산하므로 한 장 성공만으로 반드시 `COMPLETED`가 되지는 않는다.

### 12.3 탐지 결과

```sql
SELECT
    media_id,
    class_id,
    label,
    confidence,
    box_left,
    box_top,
    box_right,
    box_bottom,
    model_version,
    crop_storage_key
FROM media_analysis_detections
WHERE media_id = '<확인한 media_id>'
ORDER BY confidence DESC;
```

탐지 행이 0개여도 작업이 `COMPLETED`라면 정상이다. 이 경우 사용자 표현은 `현재 촬영 근거에서 확인 필요 관찰이 생성되지 않음`이다.

탐지 행이 있다면 다음을 추가 확인한다.

- `class_id`가 `0..12` 범위다.
- `label`, `confidence`, bbox와 `model_version`이 저장된다.
- `other`는 `class_id=12`일 때만 사용된다.
- bbox가 원본 JPEG 경계 안에 있다.
- crop이 생성된 행은 비공개 MinIO 객체가 존재한다.

## 13. 실패 처리

작업이 `FAILED`면 `failure_code`와 개인정보·비밀을 제거한 `failure_message`를 확인한다.

우선 점검 항목:

- PostgreSQL·MinIO 실행 및 `.env` 연결 정보
- MinIO 버킷과 `storage_key` 객체 존재
- JPEG가 실제 JPEG이고 2MiB 이하인지
- DB의 `width`, `height`와 실제 이미지 크기가 같은지
- 두 `best.pt`가 올바른 모델인지
- PyTorch·Ultralytics 및 CPU/CUDA 호환성
- 임시 디렉터리 생성 권한과 600초 모델 실행 제한

실패 작업을 임의 SQL로 `QUEUED`로 되돌리지 않는다. 현재 자동 재시도 계약은 미확정이므로 실패 원인과 재현 방법을 기록하고, 필요한 경우 새 테스트 JPEG로 다시 검증한다.

- Worker 계약·런타임 단위 테스트 7건이 모두 통과함
- Binary·Multiclass `best.pt`를 Ultralytics로 각각 정상 로딩함
- Spring Boot 재시작 후 Flyway V6 `create media analysis jobs`가 `success=true`로 적용됨
- 약 1분 영상에서 추출·업로드된 JPEG 21건이 모두 `QUEUED`로 등록됨
- `--once` 실행 후 `COMPLETED=1`, `QUEUED=20`으로 정확히 한 건만 처리됨을 확인함
- 나머지 20건을 처리한 뒤 `COMPLETED=21`이며 `QUEUED`와 `FAILED`가 없음을 확인함
- `media_analysis_detections`에 `other`, `crack`, `stain`, `tile_crack`, `water_damage`, `mold`, `peeling`, `trowel_mark` 원시 후보가 저장됨을 확인함
- 현재 임계값 `0.0325`에서는 낮은 신뢰도의 원시 후보가 다수 생성되므로, 사용자용 `Observation` 변환 전에 노출 임계값과 오탐 검증이 필요함

남은 확인:

- 최초 `--once` 실행 전 개별 `job_id`를 별도로 기록하지 못함
- 탐지 결과의 `crop_storage_key` 연결과 MinIO `derived/` 객체를 직접 대조하지 못함
- 원시 탐지의 사용자용 `Observation` 변환, 앱 조회와 리포트 생성은 후속 구현 범위임

따라서 JPEG 분석 파이프라인의 로컬 통합 실행은 성공했지만, 위 남은 확인과 사용자용 결과 연결 전까지 요청 전체를 최종 완료 처리하지 않는다.
