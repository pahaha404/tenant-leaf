# JPEG 사진 분석 처리 요청

## 1. 변경 배경

초기에는 서버가 원본 영상을 받아 AI 모듈에서 프레임을 추출하고 분석하는 방식을 고려했다. 그러나 MVP의 확정 흐름은 다음과 같이 변경됐다.

- 원본 영상은 사용자의 휴대전화 갤러리에만 보관한다.
- 원본 영상, 갤러리 URI와 휴대전화 파일 경로는 API·객체 저장소·PostgreSQL·AI Worker로 보내지 않는다.
- Android 앱이 촬영 종료 후 원본 영상의 **고정 3초 구간마다 JPEG 후보를 생성**한다.
- 각 구간의 앞·중간·뒤 후보 중 흔들림·밝기·중복을 비교해 최대 한 장을 선택한다.
- 선택한 JPEG만 객체 저장소에 업로드하고 AI Worker가 사진 단위로 비동기 분석한다.

따라서 이 요청서에서 `영상 업로드`, `AI Worker의 영상 열기`, `AI Worker의 프레임 추출`과 `video-jobs`는 구현 대상이 아니다. 영상은 Android에서 JPEG를 생성하기 위한 로컬 원본일 뿐이며 서버 분석 입력은 업로드가 완료된 JPEG다.

## 2. 확정된 처리 흐름

```text
AI 글래스 영상 촬영
→ 휴대전화 갤러리로 가져오기
→ Android가 고정 3초 구간마다 JPEG 후보 생성·선별
→ 미디어 등록 API로 업로드 URL 발급
→ Android가 JPEG를 객체 저장소에 직접 PUT
→ 업로드 완료 API가 객체 형식·크기 확인
→ 서버가 JPEG 분석 작업을 QUEUED로 등록
→ AI Worker가 객체 저장소의 JPEG를 내려받아 분석
→ Binary YOLO + 다중 클래스 YOLO 결과 병합
→ 서버가 결과와 모델 버전·근거 mediaId 저장
→ Android가 분석 상태와 확인 필요 관찰 후보 조회
```

서버 HTTP 요청 처리 중 무거운 모델 추론을 직접 실행하지 않는다. API는 작업을 등록하고 상태를 관리하며, 실제 추론은 별도 AI Worker가 비동기로 실행한다.

## 3. Android와 서버의 책임 구분

### Android

- 휴대전화 갤러리의 원본 영상 선택 또는 확정
- 고정 3초 구간별 JPEG 후보 생성
- 흔들림·밝기·중복 비교와 구간별 최대 한 장 선택
- JPEG 품질 `90 → 85 → 80` 조정 후 필요할 때만 픽셀 축소
- JPEG 사진당 최대 `2,097,152 bytes` 준수
- `sourceVideoId`, `sourceVideoOffsetMs`, 실제 `width`·`height` 등 메타데이터 생성
- 미디어 등록, 서명 URL 직접 업로드와 완료 확인 API 호출

### API 서버

- JPEG 메타데이터와 업로드·분석 상태 저장
- 15분 유효 서명 URL 발급
- 객체 저장소의 실제 파일 존재, JPEG 형식과 최대 2MiB 크기 검증
- `UPLOADED`로 확인된 JPEG만 분석 작업에 등록
- AI Worker 작업 상태와 결과 저장
- 사용자 소유권 검증과 인증된 결과 조회 제공
- 내부 객체 키, 로컬 경로와 서명 URL을 응답·로그에 노출하지 않음

### AI Worker

- 서버가 지정한 `mediaId`와 내부 객체 키로 JPEG 입력 확보
- 이미지 크기·디코딩 가능 여부 재검증
- 전체 이미지 Binary YOLO 추론
- 전체 이미지 다중 클래스 YOLO 추론
- 두 모델의 결과 병합
- bbox 기준 하자 영역 crop 생성
- 사진별 탐지 결과와 모델 버전을 서버에 전달
- 분석 성공·실패 상태와 실패 원인 기록

AI Worker는 원본 영상, 갤러리 URI, 휴대전화 경로를 요청하거나 영상에서 프레임을 추출하지 않는다.

## 4. 서버와 Worker 설치 항목

필수 설치:

- Python 3.14 실행 환경 권장
- `ultralytics==8.4.117`
- PyTorch 및 torchvision
- 서버 GPU를 사용할 경우 CUDA와 호환되는 PyTorch 빌드
- `opencv-python-headless`: JPEG 읽기, 검증과 crop 생성
- Pillow: 이미지 검증 및 처리
- numpy: 이미지 배열 처리

가상환경을 만든 뒤 서버 GPU·CUDA에 맞는 PyTorch와 torchvision을 공식 설치 명령으로 먼저 설치하고 `requirements.txt`를 설치한다. GPU가 없는 서버는 CPU용 PyTorch를 설치한다.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Linux 서버:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

현재 설치 대상에서 제외:

- LangGraph, LangChain, LlamaIndex
- 학습 데이터 전체와 원본 이미지·영상
- Roboflow 원본 압축 파일
- DACON, Places365 등 테스트·학습용 원본 데이터
- `runs/` 전체 학습 결과
- 영상 디코딩·프레임 추출 전용 런타임

## 5. 서버로 전달할 AI 파일

`ai-video-defect` 폴더의 구조를 유지한다.

```text
ai-video-defect/
├── requirements.txt
├── BACKEND_MODEL_OUTPUT_CONTRACT.md
├── training/
│   ├── __init__.py
│   ├── process_images_two_stage.py
│   └── predict_dacon_two_stage.py
└── models/
    └── active/
        └── two_stage_negative_rot4/
            ├── manifest.json
            ├── binary/
            │   └── best.pt
            └── multiclass/
                └── best.pt
```

서비스 사진 처리의 실행 진입점은 `training/process_images_two_stage.py`다. `training/process_video_two_stage.py`는 과거 영상 직접 분석 실험 파일로만 취급하고 MVP 서버 실행 경로에서 사용하지 않는다.

모델 가중치 원본은 일반 Git에 새로 커밋하지 않는다. 배포 환경에서는 접근 제어된 모델 저장소나 별도 배포 산출물로 제공한다.

## 6. 사진 분석 실행 예시

서비스 실행은 `mediaId` 하나와 JPEG 한 장을 입력으로 사용한다. 여러 JPEG는 미디어별 작업 여러 건으로 나누어 처리한다.

Linux 예시:

```bash
cd /server/ai-video-defect
python -m training.process_images_two_stage \
  --input /server/input/4ae76a4f-4dd9-4380-949a-8d80b47dfaa2.jpg \
  --media-id 4ae76a4f-4dd9-4380-949a-8d80b47dfaa2 \
  --job-id job-001 \
  --output /server/output/job-001
```

Windows PowerShell 예시:

```powershell
cd C:\server\ai-video-defect
python -m training.process_images_two_stage `
  --input C:\server\input\4ae76a4f-4dd9-4380-949a-8d80b47dfaa2.jpg `
  --media-id 4ae76a4f-4dd9-4380-949a-8d80b47dfaa2 `
  --job-id job-001 `
  --output C:\server\output\job-001
```

Worker가 임시 입력 파일을 만들 때 파일명을 `{mediaId}.jpg`처럼 안정된 서버 미디어 식별자와 연결한다. 분석이 끝나면 임시 입력·출력 파일은 보관 정책에 따라 정리하며 서버 내부 경로를 앱에 반환하지 않는다.

현재 활성 모델:

- Binary YOLO: `models/active/two_stage_negative_rot4/binary/best.pt`
- 다중 클래스 YOLO: `models/active/two_stage_negative_rot4/multiclass/best.pt`
- 모델 설정 및 검증 정보: `models/active/two_stage_negative_rot4/manifest.json`

## 7. AI 사진 결과 계약

사진 한 장마다 다음 기준을 사용한다.

- 결과에는 서버가 전달한 `mediaId`를 반드시 포함한다.
- 좌표는 원본 JPEG 기준 `xyxy` 픽셀 좌표다.
- 좌표 원점은 이미지 왼쪽 위 `(0, 0)`이다.
- 응답에는 실제 이미지의 `width`, `height`를 포함한다.
- 탐지 배열 이름은 `detections`다.
- 결과가 없으면 `detections: []`를 반환한다.
- 각 결과에는 `classId`, `label`, `confidence`, `box`, `modelVersion`을 보존한다.
- bbox는 이미지 경계를 벗어나지 않도록 검증한다.

예시:

```json
{
  "mediaId": "4ae76a4f-4dd9-4380-949a-8d80b47dfaa2",
  "image": {
    "width": 1920,
    "height": 1080
  },
  "modelVersion": "two_stage_negative_rot4",
  "detections": [
    {
      "classId": 1,
      "label": "mold",
      "confidence": 0.87,
      "box": {
        "left": 120,
        "top": 80,
        "right": 640,
        "bottom": 410
      }
    }
  ]
}
```

AI 모델의 서비스 라벨은 공통 계약의 13개 라벨을 따른다. 구체적인 유형으로 분류하지 못했지만 하자 후보 기준에 부합한 결과는 `classId: 12`, `label: "other"`로 반환한다. 배경, 탐지 없음, 낮은 신뢰도 또는 분석 실패를 `other`로 대신하지 않는다.

Python 사진 처리 코드는 구체 유형을 분류하지 못한 후보를 최신 공통 계약의 `other`, `classId: 12`로 반환한다. 과거 영상 실험 코드의 `unknown_defect` 출력은 MVP Worker 경로에서 사용하지 않는다.

## 8. 근거 사진과 crop

- 원본 근거는 이미 객체 저장소에 업로드된 JPEG이며 `mediaId`로 연결한다.
- 탐지 결과가 있는 경우 bbox 사방 15% 여백을 포함한 crop을 파생 이미지로 생성할 수 있다.
- crop은 원본 근거를 대체하지 않는다.
- 파생 crop을 보관할 경우 접근 제어된 객체 저장소에 저장하고 DB에는 객체 키와 메타데이터만 둔다.
- AI가 만든 로컬 `evidencePath`, `cropPath`를 API 응답에 직접 노출하지 않는다.
- 외부 응답은 권한 검증을 거친 임시 조회 URL 또는 API 조회 방식만 사용한다.
- 하나의 관찰에는 같은 임장의 업로드 완료 JPEG 1~3장을 연결하고 대표 근거를 정확히 한 장 지정한다.

여러 JPEG에 나타난 같은 흔적을 하나의 관찰로 묶는 기준은 아직 P0 미확정이다. 인접 사진 병합 규칙을 이번 구현에서 임의로 확정하지 않는다.

## 9. 서버 작업 상태

사진별 `MediaAnalysisStatus`는 다음 순서를 따른다.

```text
NOT_REQUESTED → QUEUED → ANALYZING → COMPLETED
                                  └→ FAILED
```

- `NOT_REQUESTED`: 업로드 전이거나 아직 분석 요청을 만들지 않음
- `QUEUED`: 업로드 완료 후 분석 대기
- `ANALYZING`: AI Worker가 해당 JPEG 분석 중
- `COMPLETED`: 탐지 결과가 없더라도 분석 자체가 정상 완료됨
- `FAILED`: JPEG 디코딩, 모델 실행 또는 결과 저장 실패

탐지 결과가 0건인 `COMPLETED`를 “하자 없음”으로 표현하지 않는다. 사용자에게는 “현재 촬영 근거에서 확인 필요 관찰이 생성되지 않음”으로 안내한다.

분석 자동 재시도 횟수·백오프와 `failureCode` 목록은 아직 미확정이므로 공통 계약을 먼저 보완한 뒤 구현한다.

## 10. 백엔드와 AI Worker 연결

이미 구현된 JPEG 업로드 흐름을 재사용한다.

```text
POST /api/v1/inspections/{inspectionId}/media/upload-requests
PUT  {uploadUrl}
POST /api/v1/media/{mediaId}/upload-complete
GET  /api/v1/media/{mediaId}
```

새로운 원본 영상 업로드 API와 `/video-jobs` API는 만들지 않는다.

업로드 완료 확인 후 서버는 다음 작업을 수행한다.

1. 미디어가 요청 사용자 소유의 ENDED 임장에 속하는지 확인한다.
2. `uploadStatus=UPLOADED`이며 삭제되지 않은 JPEG인지 확인한다.
3. 중복 작업이 생성되지 않도록 `mediaId` 기준으로 분석 작업을 등록한다.
4. 사진의 분석 상태를 `QUEUED`로 변경한다.
5. Worker가 작업을 가져가면 `ANALYZING`으로 변경한다.
6. 결과 검증과 저장에 성공하면 `COMPLETED`, 실패하면 `FAILED`로 변경한다.

AI Worker와 API 사이의 작업 전달 방식은 별도 프로세스 또는 큐를 사용한다. HTTP 요청을 추론이 끝날 때까지 유지하지 않는다. 큐 제품과 내부 Worker API의 정확한 형식이 아직 확정되지 않았다면 외부 OpenAPI에 임의의 경로를 추가하지 않는다.

## 11. 구현 체크리스트

- [ ] `UPLOADED` JPEG만 분석 작업에 등록
- [ ] `mediaId` 기준 중복 작업 방지
- [ ] 객체 저장소에서 JPEG를 권한 있는 내부 경로로 읽기
- [ ] 실제 JPEG 디코딩·MIME·크기 재검증
- [ ] `QUEUED → ANALYZING → COMPLETED/FAILED` 상태 갱신
- [ ] AI Worker에서 `process_images_two_stage.py` 실행
- [ ] 사진 결과에 `mediaId`, 실제 `width`·`height`, bbox와 모델 버전 포함
- [ ] `other`를 `classId: 12`로 반환하도록 AI 출력 계약 일치
- [ ] 탐지 결과가 없는 정상 분석을 `COMPLETED`로 저장
- [ ] 원시 탐지 결과를 근거 JPEG와 연결
- [ ] 파생 crop 저장 시 원본 `mediaId`와 연결
- [ ] 내부 객체 키·파일 경로·서명 URL 비노출
- [ ] 실패 원인 저장과 안전한 오류 응답
- [ ] 사용자별·매물별·임장별 소유권 검증
- [ ] 원본 영상 업로드·저장·AI 전달 코드가 없는지 확인

## 12. 테스트 범위

최소 테스트:

- JPEG 한 장 분석 성공과 빈 `detections` 성공
- 여러 JPEG 작업을 순차 또는 병렬로 처리
- 2MiB 초과, JPEG가 아닌 파일과 손상된 JPEG 거부
- 같은 `mediaId` 중복 작업 방지
- Binary·다중 클래스 결과 병합
- `other(classId=12)` 결과 저장
- bbox 이미지 경계 검증
- 객체 저장소 다운로드 실패와 모델 실패 시 `FAILED` 전이
- 다른 사용자의 미디어 분석·조회 차단
- 서버 재시작 후 작업·상태 보존

실제 Android가 생성한 JPEG와 활성 모델을 사용한 smoke test는 API와 Worker 연결 후 수행한다. 정확도 개선, threshold 조정, 추가 데이터 수집, 성능 최적화와 UI 개선은 이 요청서의 구현 완료 조건에 포함하지 않는다.

## 13. LangGraph 도입 시점

LangGraph는 현재 서버 설치와 배포 대상에 포함하지 않는다. 먼저 다음을 완료한다.

1. `ai-video-defect` 사진 처리 모듈 배포
2. 객체 저장소 JPEG와 AI Worker 연결
3. Binary·다중 클래스 YOLO 추론과 결과 저장 검증
4. 근거 JPEG·crop·관찰 후보 연결 검증
5. 실패 상태와 재실행 정책 확정

이후 필요할 때만 처리 단계별 상태 관리, 실패 단계 재실행과 사용자 확인 분기를 관리하는 용도로 LangGraph를 검토한다. 모델 자체를 대체하는 용도로 사용하지 않으며 현재 `requirements.txt`에는 추가하지 않는다.

## 14. 구현 현황 (2026-08-20)

구현됨:

- 업로드 완료 JPEG를 `mediaId` 기준으로 한 번만 `QUEUED` 작업에 등록
- 분석 작업과 원시 탐지 결과를 저장하는 Flyway V6 테이블
- PostgreSQL 작업을 선점해 MinIO JPEG를 내려받는 Python Worker
- JPEG 2MiB·형식·픽셀 크기 재검증
- 사진 한 장 단위 두 단계 YOLO 실행과 `mediaId`·모델 버전 결과 검증
- `other(classId=12)` 출력 계약과 bbox 이미지 경계 검증
- `QUEUED → ANALYZING → COMPLETED/FAILED` 미디어·임장 집계 상태 갱신
- crop의 비공개 MinIO 저장과 원시 탐지 DB 연결

아직 검증되지 않음:

- 저장소 정책상 포함되지 않은 Binary·다중 클래스 `best.pt`를 사용한 실제 추론
- Python 3.11/3.12, Docker와 PostgreSQL·MinIO가 모두 있는 환경의 Worker 통합 테스트
- 여러 JPEG 작업의 실제 처리량과 장시간 안정성

외부 관찰 조회 API, 인접 JPEG 병합, 자동 재시도 정책은 기존 미확정 범위를 유지하며 이번 구현에서 임의로 추가하지 않았다.
