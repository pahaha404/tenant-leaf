# 세입세잎 도메인 규칙

> 상태: 검토 초안 0.7
> 기준일: 2026-08-25
> 최우선 기준: `스트리밍 분석 폐지요청`, `체크리스트 중심 계약 → 구역·관찰·근거 미디어 중심 계약 전환`, `17. 리포트 분석을 위한 공통 api 계약 보완` 요청
> 참고 문서: `세입세잎 전체 서비스 플로우.md`, `../../team/00_shared/공통 api 계약.md`, `../../design/UI/UI.pen`

## 1. 목적과 기준 우선순위

이 문서는 세입세잎의 현장 점검을 **구역·관찰·근거 미디어 중심**으로 구현하기 위한 업무 규칙을 정의한다. Android, API, AI Worker와 리포트가 같은 의미를 사용하도록 도메인 경계와 불변 조건을 정리한다.

판단 우선순위는 다음과 같다.

1. `스트리밍 분석 폐지요청`과 `체크리스트 중심 계약 → 구역·관찰·근거 미디어 중심 계약 전환` 요청
2. 루트와 서버 `AGENTS.md`의 개인정보·AI·보안 원칙
3. 기존 공통 API 계약과 전체 서비스 플로우
4. 아직 수정 중인 `UI.pen`

최우선 변경 요청과 충돌하는 기존 API·OpenAPI·UI는 구현 기준으로 사용하지 않는다. 이 문서의 **결정 필요** 항목은 팀 합의 전까지 API enum이나 DB 컬럼으로 확정하지 않는다.

## 2. 핵심 변경

```text
[이전]
28개 체크리스트 → 항목별 사용자 상태 → 체크리스트 완료율

[변경]
AI 글래스 기본 고화질 영상 촬영 → 휴대전화 갤러리로 가져오기
→ 촬영 중 생성하거나 촬영 후 추출한 JPEG 업로드 → 구역 분류·하자 의심 관찰 생성
→ 근거 사진 연결 → 사용자가 구역별 결과 확인 → 리포트 생성
```

MVP에서는 카메라 스트림을 서버로 전송하거나 촬영 중 AI 분석을 실행하지 않는다. 촬영 중 정지 사진 동시 생성은 Meta SDK와 실기기가 기본 영상 녹화를 방해하지 않을 때만 사용하며, MVP의 보장 경로는 촬영 완료 후 Android가 원본 영상에서 고정 3초 간격으로 JPEG 후보를 추출하는 방식이다.

현장 점검에서는 다음 개념을 사용하지 않는다.

- 체크리스트 항목별 상태 입력과 최종 확정
- 체크리스트 완료율
- AI와 특정 체크리스트 항목의 매칭
- AI 결과로 `문제 없음`, `문제 있음`, `하자 발견`을 확정하는 기능

방문 전 학습용 **안심 가이드**는 유지하지만 임장 세션, AI 분석 결과 또는 리포트 데이터와 연결하지 않는다.

## 3. 핵심 도메인 관계

```text
User
 └─ Property
     └─ InspectionSession
         ├─ LocalRecordedVideo (Android 휴대전화 전용)
         │    └─ AnalysisFrame 후보
         ├─ Media(PHOTO) ─ MediaAnalysis
         │            ├─ Zone 분류
         │            └─ Observation 후보 생성
         ├─ ZoneAnalysisStatus (구역별 분석 집계)
         ├─ Observation ─ EvidenceMedia
         ├─ UserMemo (상세 계약 미정)
         └─ Report

SafetyGuide (임장·분석과 분리된 학습 콘텐츠)
```

- 원본 영상은 휴대전화에만 저장하고 API·객체 저장소·PostgreSQL에는 업로드하지 않는다.
- 분석 사진은 하나의 임장과 로컬 원본 영상의 시점에 연결하며 AI가 구역과 신뢰도를 기록한다.
- 관찰 결과는 같은 임장의 근거 미디어 하나 이상과 연결한다.
- 구역별·임장 전체 분석 상태는 개별 미디어 처리 결과의 집계다.
- 리포트는 매물, 임장, 구역별 상태, 관찰, 근거 미디어와 사용자 메모로 만든 파생 결과다.

## 4. 전체 불변 조건

1. 사용자는 자신이 앱에 등록한 매물 기록과 그 하위 임장·미디어·관찰·리포트에만 접근할 수 있다. 이는 부동산의 법적 소유권이 아니라 앱 데이터 접근 권한이다.
2. 흐름은 `AI 글래스 기본 영상 촬영 → Meta AI 동반 앱을 통한 휴대전화 갤러리 가져오기 → Android JPEG 생성 → API → Object Storage → AI Worker → API DB → Android` 순서를 지킨다.
3. AI 글래스는 API나 AI 제공자를 직접 호출하지 않는다.
4. Android는 AI 제공자 API 키를 저장하거나 AI 제공자를 직접 호출하지 않는다.
5. MVP는 촬영 중 실시간 AI 분석을 하지 않으며 촬영 종료 후 업로드된 JPEG만 비동기로 분석한다.
6. AI는 분석 사진의 구역 분류와 하자 의심 흔적 관찰만 수행한다.
7. AI는 물건 식별, 실제 하자·안전·수리 필요·법률 판단·계약 가능 여부를 확정하지 않는다.
8. 관찰 결과는 반드시 서버에 업로드된 근거 사진으로 추적할 수 있어야 한다.
9. `confidence`는 모델 신뢰도이며 위험도나 안전 점수가 아니다.
10. 서버가 받는 JPEG는 PostgreSQL이 아닌 접근 제어된 객체 저장소에 둔다.
11. 휴대전화의 원본 영상 경로·갤러리 URI는 API로 전송하거나 서버에 저장하지 않는다.
12. 저장소 내부 키와 만료되지 않는 사진 URL을 Android에 노출하지 않는다.
13. 일부 사진 실패가 임장 전체 실패로 전파되어서는 안 된다.
14. 완료된 구역 결과는 다른 구역이 분석 중이거나 실패해도 조회할 수 있어야 한다.
15. 요청 재전송으로 중복 사진·관찰·알림이 생기지 않아야 한다.
16. 화면과 리포트는 `확인 필요 관찰`, `하자 의심 흔적`, `근거 사진`처럼 비확정 표현을 사용한다.

## 5. 사용자와 인증 `User`

- MVP는 실제 소셜 계정과 연결되지 않은 데모 사용자를 사용한다.
- API는 접근 토큰의 사용자 ID로 모든 하위 리소스의 데이터 접근 권한을 검사한다.
- 이메일·카카오·네이버·Google UI가 있더라도 MVP에서 실제 인증 완료로 표현하지 않는다.
- 사용자는 관찰 결과를 열람하고 리포트에서 제외할 수 있다.

### 결정 필요

- 데모 토큰 만료 시간과 재로그인 기준
- 온보딩·안심 가이드 완료 상태를 로컬 또는 서버 중 어디에 저장할지
- 푸시 토큰 등록·교체·삭제 API와 알림 동의 철회 방식

## 6. 매물 `Property`

- 필수: `id`, 등록 사용자 ID, `name`, 생성·수정 시각
- 선택: 주소 요약, 보증금, 월세, 관리비, 전용면적(㎡), 층, 옵션, 부동산 연락처, 메모
- 사용자가 앱에 등록한 매물만 임장을 생성할 수 있다.
- 금액은 원 단위 0 이상 정수, 면적은 0보다 큰 ㎡ 기준값으로 저장한다.
- Android가 평 입력값을 `1평 = 3.305785㎡`로 변환하며 평 값을 중복 저장하지 않는다.
- 주소는 비교에 필요한 최소 요약만 저장한다.
- 층·옵션·부동산 연락처는 사용자 참고 정보이며 서버가 정확성을 보증하지 않는다.
- 최근 점검·리포트 상태는 하위 데이터에서 계산하고 매물에 중복 저장하지 않는다.

### 결정 필요

- 주거 형태와 방문 예정일을 매물에 둘지 별도 일정으로 분리할지
- 임장이 있는 매물 삭제 시 하위 데이터 처리 방식
- 즉시 삭제와 복구 가능한 보관 중 어떤 정책을 사용할지

## 7. 임장 세션 `InspectionSession`

임장 세션은 특정 매물을 한 번 방문해 미디어를 수집하고 분석하는 기록이다.

- 필수: `inspectionId`, `propertyId`, 사용자 ID, `status`, `analysisStatus`, `startedAt`
- 선택: `endedAt`, `cancelledAt`, `archivedAt`, `mediaFinalizedAt`, `expectedMediaCount`
- 파생값: 로컬 원본 영상 수, 분석 사진 수, 인식 구역 목록, 전체 관찰 수, 완료 구역 수, 전체 정규 구역 수

### 세션 상태

```text
IN_PROGRESS → ENDED
      └────→ CANCELLED
```

| 값 | 의미 |
|---|---|
| `IN_PROGRESS` | 안경으로 현장 원본 영상을 촬영 중 |
| `ENDED` | 사용자가 현장 촬영을 종료했으며 영상 가져오기·사진 생성·업로드·분석 가능 |
| `CANCELLED` | 사용자가 촬영을 중단해 업로드·분석 대상에서 제외됨 |

### 전체 분석 상태

| 값 | 의미 |
|---|---|
| `NOT_STARTED` | 분석 대상 업로드 또는 요청 전 |
| `UPLOADING` | 미디어 등록·업로드·객체 확인 또는 업로드 재시도 단계 |
| `QUEUED` | 업로드 완료 후 분석 요청 준비 또는 대기열 처리 중 |
| `ANALYZING` | 하나 이상의 미디어 분석 중 |
| `PARTIAL_COMPLETED` | 일부 결과 조회 가능, 나머지는 진행 중 또는 실패 |
| `COMPLETED` | 미디어 집합 확정 후 모든 분석 대상 처리가 성공함 |
| `FAILED` | 미디어 집합 확정 후 조회 가능한 성공 결과 없이 모든 대상이 최종 실패함 |

### 세션 규칙

- 장비·권한 확인은 Android의 준비 화면에서 수행하고, 사용자가 실제 촬영을 시작할 때 서버에 `IN_PROGRESS` 세션을 생성한다.
- MVP에서는 `IN_PROGRESS` 동안 서버 업로드와 AI 분석을 시작하지 않는다.
- 종료 시 `ENDED`와 `endedAt`을 기록한 뒤 휴대전화 영상 가져오기, JPEG 생성, 업로드와 비동기 분석을 시작한다.
- 중간에 포기하면 `CANCELLED`와 `cancelledAt`을 기록하고 해당 세션의 신규 업로드와 분석을 허용하지 않는다.
- `ENDED`와 `CANCELLED`는 되돌릴 수 없는 최종 상태다. 재방문하거나 다시 촬영하면 새 세션을 만든다.
- 목록 보관은 세션 상태를 바꾸지 않고 `archivedAt`으로 관리한다. 보관과 삭제는 서로 다른 동작이다.
- 공통 API 계약 2.2 검토 초안과 OpenAPI에서는 세션 종료 값을 `ENDED`로 통일한다. 기존 1.2의 `completed`와 새 값을 섞어 사용하지 않는다.
- 분석 사진은 `ENDED` 상태에서 등록할 수 있으며 리포트가 확정된 뒤에는 추가 등록하지 않는다.
- `잠시 멈추기`는 안경의 기본 영상 녹화 제약에 따라 현재 클립을 종료하고 새 클립으로 재개할 수 있으며 세션은 `IN_PROGRESS`를 유지한다.
- `detectedZones`와 `analysisSummary`는 원본 데이터에서 계산하며 직접 수정하지 않는다.

### 전체 분석 상태 집계

Android가 전체 분석 상태나 집계 수치를 직접 확정하지 않는다. 서버가 삭제되지 않은 등록 미디어의 업로드·분석 상태와 `mediaFinalizedAt` 존재 여부를 기준으로 아래 우선순위에 따라 계산한다. `mediaFinalizedAt`이 있으면 분석 대상 미디어 집합이 확정된 것이다.

1. 등록 미디어가 없으면 집합 확정 여부와 관계없이 `NOT_STARTED`다.
2. 성공한 분석이 하나 이상이고, 집합이 미확정이거나 다른 미디어가 진행 중·최종 실패 상태면 `PARTIAL_COMPLETED`다.
3. 성공한 분석이 없고 분석 중인 미디어가 있으면 `ANALYZING`이다.
4. 성공·분석 중 미디어가 없고 `analysisStatus=QUEUED`이거나 `uploadStatus=UPLOADED`이면서 `analysisStatus=NOT_REQUESTED`인 미디어가 있으면, 집합 확정 여부와 관계없이 `QUEUED`다.
5. 위 상태가 없고 `PENDING`, `UPLOADING`, 재시도 가능한 업로드 `FAILED`가 있거나, 집합 미확정 상태에서 등록 미디어가 업로드·분석 최종 실패만 남은 경우에는 아직 등록 단계가 열려 있으므로 `UPLOADING`이다.
6. 미디어 집합이 확정되고 모든 등록 미디어의 분석이 성공했을 때만 `COMPLETED`다.
7. 미디어 집합이 확정되고 성공한 분석이 하나 이상이며 나머지가 모두 최종 실패면 `PARTIAL_COMPLETED`다.
8. 미디어 집합이 확정되고 성공한 분석 없이 모든 등록 미디어가 업로드 또는 분석 단계에서 최종 실패했을 때만 `FAILED`다.

- `COMPLETED`와 `FAILED`는 미디어 집합 확정 전에는 반환하지 않으며, 한 번 반환한 뒤 신규 미디어 추가로 진행 상태로 되돌아가지 않는다.
- 업로드 `FAILED`가 자동 재시도 가능한지 또는 최종 실패인지 서버가 구분해야 한다.
- 분석 결과가 관찰 0건이어도 미디어 분석 자체가 성공했다면 완료된 분석으로 집계한다.
- 성공한 결과는 다른 미디어의 진행·실패와 관계없이 즉시 조회할 수 있다.

### 남은 결정

- `archivedAt` 설정·해제 주체와 삭제 API의 차이
- 동일 사용자·매물에서 동시 진행 세션을 허용할지

## 8. 구역 `Zone`

| API 값 | 앱 표시 |
|---|---|
| `KITCHEN` | 주방 |
| `LIVING_ROOM` | 거실·방 |
| `BATHROOM` | 화장실 |
| `UNKNOWN` | 구역 확인 필요 |

- AI가 분류하는 정규 구역은 `KITCHEN`, `LIVING_ROOM`, `BATHROOM` 세 개로 제한한다.
- 현관과 창틀은 현재 AI 분류 범위에서 제외한다. 해당 공간이 촬영되었거나 분류 결과가 지원 범위를 벗어나면 `UNKNOWN`으로 정규화한다.
- AI Worker가 구역 분류 API를 호출하며 Android는 AI 제공자를 직접 호출하지 않는다.
- AI 구역 분류가 성공하고 확실한 경우 `aiZone`에 해당 구역을 저장한다. 불확실하거나 API 호출에 실패했거나 지원하지 않는 응답이면 `aiZone=UNKNOWN`, `zoneUncertain=true`로 저장한다.
- 모든 분류에 `aiZone`, `zoneConfidence`, `zoneUncertain`, `zoneModelVersion`을 함께 저장한다.
- `UNKNOWN`은 3개 정규 구역 완료 수에 포함하지 않는다.
- `UNKNOWN` 미디어는 임의의 정규 구역에 배분하지 않고 앱에서 `구역 확인 필요` 묶음으로 노출한다.
- P1에서 사용자가 구역을 보정할 수 있게 하되 AI 원본 결과를 덮어쓰지 않는다. `userCorrectedZone`, 수정자와 `correctedAt`을 별도로 기록하고 원래 값으로 되돌릴 수 있게 한다.
- 화면과 리포트의 유효 구역은 `userCorrectedZone`이 있으면 이를 우선하고, 없으면 `aiZone`을 사용한다.
- 구역은 공간 범주이며 특정 물건이나 체크리스트 항목 식별이 아니다.

### 결정 필요

- `UNKNOWN` 판정의 신뢰도 임계값
- 사용자 구역 보정 UI와 수정 이력 조회 범위
- 여러 구역을 포함한 원본 영상에서 추출한 프레임의 구역 안정화 방식

## 9. 원본 영상과 분석 사진 `LocalRecordedVideo`, `Media`

### 원본 영상 `LocalRecordedVideo`

- 안경의 기본 고화질 녹화 기능으로 촬영하고 Meta AI 동반 앱의 가져오기 기능을 통해 사용자의 휴대전화 갤러리에 저장한다.
- MVP가 보장하는 기본 흐름은 `안경 기본 녹화 → 휴대전화 갤러리 가져오기 → 앱에서 영상 선택 → 촬영 후 JPEG 추출`이다.
- 촬영 중 JPG 생성은 기본값을 끈 실험 기능으로 두고, 실기기에서 원본 영상 중단·손상·화질 저하와 시점 오차가 없음을 검증한 기기에서만 활성화한다.
- 서버·AI Worker·객체 저장소에는 원본 영상 파일을 업로드하지 않는다.
- Android는 임장 안에서 여러 영상 클립의 순서를 관리하기 위해 클립마다 `sourceVideoId`를 생성한다.
- 갤러리 URI와 로컬 파일 경로는 Android 로컬에서만 관리하며 API 요청, 로그와 분석 결과에 포함하지 않는다.
- 사용자가 갤러리 원본을 삭제하면 원본 재생은 불가능하지만 이미 업로드된 근거 사진과 분석 결과는 각 보관 정책에 따라 유지한다.

### 분석 사진 `Media(PHOTO)`

- 필수: `mediaId`, `clientMediaId`, `inspectionId`, `sourceVideoId`, `frameOrigin`, `sourceVideoOffsetMs`, `captureSource`, `capturedAt`, 업로드·분석 상태
- 선택: AI 구역·신뢰도·불확실 여부·모델 버전, 사용자 보정 구역·보정 시각, 크기·해상도
- 내부 전용: 객체 저장소 `storageKey`
- 조회용: 요청 시 발급하는 짧은 만료 시간의 서명 URL

```text
mediaType: PHOTO
captureSource: META_GLASS | ANDROID_CAMERA
frameOrigin: DURING_RECORDING_CAPTURE | POST_RECORDING_EXTRACTION
uploadStatus: PENDING | UPLOADING | UPLOADED | FAILED
analysisStatus: NOT_REQUESTED | QUEUED | ANALYZING | COMPLETED | FAILED
```

- `DURING_RECORDING_CAPTURE`는 안경 기본 영상 녹화를 유지하면서 공식 SDK와 실기기에서 정지 사진 동시 생성이 검증된 경우에만 사용한다.
- `POST_RECORDING_EXTRACTION`은 촬영 완료 후 Android가 휴대전화의 원본 영상에서 프레임을 추출한 경우다.
- `sourceVideoId`는 Android가 생성한 불투명 UUID이며 서버의 영상 파일 ID가 아니다.
- `sourceVideoOffsetMs`는 해당 사진이 원본 영상 시작 후 몇 밀리초 지점인지 나타낸다.
- `capturedAt`은 동시 촬영 시 실제 캡처 시각, 사후 추출 시 원본 영상 시작 시각과 `sourceVideoOffsetMs`로 계산한 촬영 시각이다.

### 업로드·근거 규칙

- 업로드 흐름은 `등록 → 서명 URL 발급 → JPEG 직접 업로드 → 완료 확인 → 분석 요청` 순서다.
- Android가 `ENDED` 세션의 촬영 종료 후 API에서 URL을 받아 분석 사진을 객체 저장소에 직접 업로드한다.
- 등록 API는 `items` 배열로 최소 1장, 최대 20장을 받는다. 이는 요청 한 번의 묶음 한도이며 임장 전체 사진 수 제한이 아니다.
- 10분 영상을 고정 3초 간격으로 처리해 약 200장을 선택하면 20장씩 약 10개의 등록 요청으로 나눈다.
- 서명 업로드 URL은 발급 시점부터 15분 동안 유효하며 URL과 서명 값은 로그나 영구 저장소에 남기지 않는다.
- Android는 논리적으로 같은 사진에 재시도에도 변하지 않는 `clientMediaId` UUID를 생성한다. `(inspectionId, clientMediaId)` 조합은 중복될 수 없다.
- 같은 `(inspectionId, clientMediaId)`와 같은 메타데이터의 재등록은 기존 미디어를 재사용하고, 다른 메타데이터면 `409 CLIENT_MEDIA_ID_CONFLICT`로 거부한다.
- 업로드 등록·완료·재시도 요청은 `Idempotency-Key`를 사용한다. 같은 키와 같은 요청은 기존 결과를 반환하고 중복 DB 행이나 객체를 만들지 않는다.
- 같은 사용자·HTTP 메서드·경로에서 같은 키를 다른 요청 내용에 재사용하면 `409 IDEMPOTENCY_KEY_CONFLICT`를 반환한다.
- API는 객체 존재·크기·형식을 확인한 후에만 `UPLOADED`로 확정한다.
- `UPLOADED` 미디어만 분석할 수 있다.
- 실패 미디어는 같은 `mediaId`, `clientMediaId`와 저장소 키를 유지한 채 새 서명 URL만 발급해 자동으로 최대 3회 재시도한다. 이후에는 사용자가 직접 재시도한다.
- 성공 미디어는 다시 업로드하지 않고 성공 객체를 중복 생성하지 않는다.
- Android는 모든 분석 대상 미디어 등록을 마치면 `expectedMediaCount`와 `Idempotency-Key`로 미디어 집합 확정 API를 호출한다.
- 서버는 임장이 `ENDED`이고 삭제되지 않은 등록 미디어 수가 `expectedMediaCount`와 일치할 때 `mediaFinalizedAt`을 기록한다.
- 확정 후 신규 미디어 등록은 `409 MEDIA_SET_FINALIZED`, 등록 수가 다르면 `409 MEDIA_SET_COUNT_MISMATCH`로 거부한다. 이미 등록된 실패 미디어 재시도는 허용한다.
- 같은 멱등성 키와 같은 요청을 재전송하면 최초 결과를 반환한다. 같은 키를 다른 요청에 재사용하면 `409 IDEMPOTENCY_KEY_CONFLICT`다.
- 확정된 미디어 집합을 분석·리포트 집계 분모로 사용한다.
- `UPLOADING`은 Android가 확정해 보내는 값이 아니라 등록 미디어와 객체 저장소 상태를 바탕으로 서버가 계산한다.
- `thumbnailUrl`은 영구 저장값이 아니라 조회 시 발급하는 서명 URL이다.
- 관찰 근거는 같은 임장의 검증된 사진이어야 한다.
- 음성은 현재 시각적 관찰의 근거로 사용하지 않는다.
- 근거 삭제 시 관찰·리포트에 `근거 사진 사용 불가`를 표시할 수 있어야 한다.

### 업로드 HTTP 경계

```text
POST /inspections/{inspectionId}/media/upload-requests
POST /inspections/{inspectionId}/media/finalize
POST /media/{mediaId}/upload-complete
POST /media/{mediaId}/upload-retry
GET  /inspections/{inspectionId}/media
GET  /media/{mediaId}
```

- 등록·재시도는 `ENDED` 임장에서만 허용하고 `IN_PROGRESS`, `CANCELLED`에서는 거부한다.
- 1~20장 등록 배치는 원자적으로 처리하며 한 항목이라도 검증에 실패하면 새 항목을 하나도 생성하지 않는다.
- 등록 항목은 `clientMediaId`, `contentType=image/jpeg`, `fileSize`, 실제 `width`·`height`, `sourceVideoId`, `sourceVideoOffsetMs`, `frameOrigin=POST_RECORDING_EXTRACTION`, `captureSource`, `capturedAt`을 포함한다. 구역은 Android 등록값이 아니라 AI 분석 결과다.
- 등록 응답은 같은 순서의 항목별 `mediaId`, `clientMediaId`, 15분 서명 `uploadUrl`, `expiresAt`, `uploadStatus=PENDING`을 제공한다.
- Android는 서명 URL로 객체 저장소에 JPEG를 직접 `PUT`하며 API가 파일 바이트를 중계하지 않는다.
- 완료 API는 객체 존재, 실제 JPEG 형식, MIME, 최대 2MiB와 메타데이터를 확인한 경우에만 `UPLOADED`로 바꾼다.
- 재시도 API는 같은 미디어·저장소 키에 새 서명 URL만 발급한다. Android 자동 재시도는 최대 3회이고 이후에는 사용자 행동이 있어야 한다.
- 목록은 0부터 시작하는 `page`, `size`를 사용한다. 다른 사용자 리소스는 `404`로 숨긴다.
- 임장당 전체 미디어 상한은 별도 P0 결정 대상이며, 요청당 20장 제한을 임장 전체 제한으로 해석하지 않는다.

### 사진 규격과 보관

- 자동 분석 사진은 JPEG(`.jpg`, `.jpeg`, MIME `image/jpeg`)만 허용한다.
- 촬영 중 동시 사진 생성은 기본 영상 녹화를 중단하거나 화질을 낮추면 사용하지 않고 촬영 후 추출 방식으로 되돌린다.
- MVP 기본값은 Android가 촬영 완료 후 원본 영상의 고정 3초 구간마다 사진을 생성하는 방식이다.
- 각 3초 구간의 앞·중간·뒤에서 후보를 만들고 흔들림·밝기·직전 선택 사진과의 중복을 비교해 최대 한 장을 선택한다.
- 모든 후보가 흐리거나 어두워도 그중 가장 나은 한 장을 남기고 `화질 확인 필요` 상태를 표시한다.
- 원본 영상 프레임의 실제 해상도를 기록하고 고정된 스트림 해상도나 프레임률을 계약값으로 사용하지 않는다.
- 실제 영상 시점은 디코더가 제공하는 값을 기준으로 `sourceVideoOffsetMs`에 기록한다.
- JPEG 품질은 90에서 시작하고 2MiB를 넘으면 85, 80 순서로 조정한 뒤에도 초과할 때만 픽셀 크기를 단계적으로 줄인다.
- 서버 최대 크기는 사진당 2MiB이며 실제 형식·MIME·크기·해상도를 검증한다.
- 실패·미완료 파일은 최대 24시간, 관찰 없는 자동 사진은 분석 후 최대 7일 보관한다.
- 관찰 근거 또는 중요 사진은 임장 종료 후 최대 30일 보관한다.
- 삭제 임장 미디어는 즉시 사용 중단 후 최대 7일 안에 완전 삭제한다.
- 위 보관·삭제 기한은 MVP 정책 방향으로 확정한다. 실제 업로드 기능을 열기 전 서버 정리 작업과 삭제 이력을 구현하고 자동 집행 여부를 검증한다.

### 결정 필요

- 실기기에서 기본 영상 녹화와 정지 사진 동시 생성이 가능한지, 영상 중단·화질 저하가 없는지
- 기본 녹화 시작 시각을 앱이 확인해 동시 생성 사진의 `sourceVideoOffsetMs`를 계산할 수 있는지
- 지원 안경 모델의 기본 영상 코덱·해상도·클립 최대 길이와 휴대전화 가져오기 완료 판별 방식
- 대표 하자 사진의 AI 성능 비교를 통해 2MiB 제한에서 세부 흔적 보존과 저장 용량이 적절한지 확인할 기준
- 휴대폰 마이크용 별도 `captureSource`
- 휴대전화 원본 영상 삭제 안내와 세입세잎 앱의 로컬 참조 정리 방식

## 10. 미디어 분석 `MediaAnalysis`

```text
NOT_REQUESTED → QUEUED → ANALYZING → COMPLETED
                              └────→ FAILED
```

- HTTP 요청 중 무거운 추론을 실행하지 않고 작업 큐에 등록한다.
- AI Worker는 업로드된 JPEG별 하자 원시 탐지와 AI 구역 분류 결과를 반환한다.
- bbox는 EXIF 방향을 정규화한 원본 전체 JPEG의 픽셀 `xyxy(left, top, right, bottom)`와 해당 이미지 `width`·`height`를 함께 보존한다. Android에는 AI가 본 것과 동일한 방향·비율의 JPEG를 제공하며 화면 좌표 변환값으로 원본 bbox를 덮어쓰지 않는다.
- AI 원시 탐지 수집 기준 `0.0325`는 사용자 표시 기준이 아니다. 원시 탐지는 기준 이상이면 DB에 보존한다.
- 관찰은 모델 버전과 라벨별 설정인 `modelVersion`, `classId`, `observationMinConfidence`, `configuredAt`을 적용해 생성한다. 숫자 임계값은 OpenAPI에 고정하지 않는다.
- 관찰 생성 임계값 미만의 원시 탐지는 관찰로 만들지 않지만 모델 개선과 감사용 원시 결과로 보존한다.
- 구역 분류는 AI API 성공·확실 결과만 정규 구역으로 저장하고, 불확실·실패·미지원 응답은 `UNKNOWN`으로 정규화한다.
- AI Worker는 휴대전화의 원본 영상을 요청하거나 직접 분석하지 않는다.
- API는 미디어·임장 ID, enum, 신뢰도와 모델 버전을 검증한다.
- 같은 결과가 재전송돼도 관찰이 중복 생성되지 않아야 한다.
- 성공 결과는 다른 미디어 실패 때문에 폐기하지 않는다.
- 내부 제공자 오류는 Android에 직접 노출하지 않는다.
- MVP AI Worker는 JPEG 분석만 담당하며 음성·STT 작업은 포함하지 않는다.

### 인접 사진 관찰 병합

- 같은 임장, 같은 유효 구역, 같은 `ObservationType`, `sourceVideoOffsetMs` 차이 6초 이내이며 crop 이미지 유사도가 설정 기준 이상일 때만 같은 관찰로 병합한다.
- 병합된 관찰은 근거 사진을 최대 3장만 유지하고 신뢰도가 가장 높은 사진을 대표 근거로 지정한다.
- crop 이미지 유사도 비교가 구현되지 않았거나 계산에 실패하면 자동 병합하지 않는다. 시간과 라벨만으로 병합하지 않는다.

### 결정 필요

- 라벨별 `observationMinConfidence`와 crop 유사도 임계값의 모델 버전별 검증값
- 자동 재시도 횟수, 백오프, 재시도 가능한 오류와 최종 `failureCode` 목록
- 재분석 이력 보존 또는 기존 결과 교체 방식
- 실제 기기·영상 표본으로 보정할 선명도·밝기·중복 판정 임계값

## 11. 구역별 분석 상태 `ZoneAnalysisStatus`

| 값 | 앱 처리 |
|---|---|
| `NO_MEDIA` | 아직 해당 구역 미디어 없음 |
| `UPLOADING` | 미디어 업로드 중 |
| `QUEUED` | 분석 대기 중 |
| `ANALYZING` | AI 분석 중 |
| `COMPLETED` | 결과 상세 진입 가능 |
| `PARTIAL_FAILED` | 완료 결과 표시, 실패 미디어만 재시도 |
| `FAILED` | 재시도 버튼 표시 |

- 구역별 분석 사진 수, 관찰 수, 실패 사진 수, 재시도 가능 여부와 갱신 시각을 제공한다.
- 각 정규 구역은 독립적으로 상태가 전환된다.
- `NO_MEDIA`는 하자 미탐지가 아니라 해당 구역에 분류된 분석 사진이 없다는 뜻이다.
- 진행 중 미디어가 없고 성공과 실패가 함께 있으면 `PARTIAL_FAILED`, 성공만 있으면 `COMPLETED`, 실패만 있으면 `FAILED`다.
- 분석 중·대기·업로드 상태가 함께 있으면 `ANALYZING > QUEUED > UPLOADING` 순서로 우선 표시하고 완료 결과 존재 여부를 `hasResults`로 함께 제공한다.
- 완료 구역은 다른 구역 상태와 관계없이 조회할 수 있다.
- 분석이 성공했지만 관찰이 0건인 미디어도 성공으로 집계한다.
- `UNKNOWN` 미디어는 별도의 `구역 확인 필요` 집계로 제공하고 정규 구역 완료 수에 포함하지 않는다.
- 분석 대상 미디어 집합이 확정된 뒤에는 신규 미디어를 추가하지 않으므로 `COMPLETED`가 다시 진행 상태로 돌아가지 않는다.
- 집계 수치는 서버가 원본 데이터에서 계산한다.

## 12. 관찰 결과 `Observation`

관찰은 AI가 촬영 장면에서 생성한 **하자 의심 흔적**이며 실제 하자 판정이 아니다.

- 필수: `observationId`, `inspectionId`, 유효 구역, `ObservationType`, 비확정 제목·설명, 신뢰도, 상태, 원본 `classId`·정규화 라벨·모델 버전, 생성 시각
- 근거: 같은 임장의 업로드 완료 JPEG 최소 1장, 최대 3장

### AI 라벨과 관찰 유형

문자열 철자가 아니라 `classId`를 기준으로 아래 1:1 변환을 적용한다. Worker는 `water_damage`, `tile_crack`처럼 들어오는 별칭을 계약의 정규 라벨로 바꿔 저장한다.

| classId | 정규 AI 라벨 | `ObservationType` |
|---:|---|---|
| 0 | `crack` | `CRACK_CHECK_NEEDED` |
| 1 | `mold` | `MOLD_CHECK_NEEDED` |
| 2 | `peeling` | `PEELING_CHECK_NEEDED` |
| 3 | `waterdamage` | `WATER_DAMAGE_CHECK_NEEDED` |
| 4 | `tiledamage` | `TILE_DAMAGE_CHECK_NEEDED` |
| 5 | `hole` | `HOLE_CHECK_NEEDED` |
| 6 | `tilecrack` | `TILE_CRACK_CHECK_NEEDED` |
| 7 | `paintdrips` | `PAINT_DRIPS_CHECK_NEEDED` |
| 8 | `pinhole` | `PINHOLE_CHECK_NEEDED` |
| 9 | `surfacedefect` | `SURFACE_DEFECT_CHECK_NEEDED` |
| 10 | `stain` | `STAIN_CHECK_NEEDED` |
| 11 | `trowelmark` | `TROWEL_MARK_CHECK_NEEDED` |
| 12 | `other` | `OTHER_CHECK_NEEDED` |

`TOILET_FAUCET_BROKEN`, `DEFECT_CONFIRMED`, `SAFE`, `NO_PROBLEM`처럼 물건 고장이나 상태를 확정하는 값을 만들지 않는다.

### AI 라벨 `other(기타)` 반영

- AI 모델의 하자 분류는 기존 12개 라벨에 `other`를 추가한 총 13개 라벨로 관리한다.
- `other`의 모델 클래스 ID는 `12`, 영문 원본 라벨은 소문자 `other`, 한글 표시명은 `기타`다.
- 모델이 하자 기준에 부합하는 후보를 탐지했지만 기존 클래스 ID `0`~`11` 중 구체적인 종류를 분류하지 못한 경우에만 `other`를 사용한다.
- `other`는 배경, 하자 후보 없음, 낮은 신뢰도만 있는 결과 또는 분석 실패를 대신하는 값이 아니다.
- `other` 모델 결과는 도메인의 `OTHER_CHECK_NEEDED` 관찰 유형으로 변환한다.
- `OTHER_CHECK_NEEDED`도 확정된 하자 판정이 아니며, 근거 사진과 함께 사용자가 확인해야 하는 관찰 후보로 표시한다.
- 결과에는 원본 라벨 `other`, 클래스 ID `12`, 신뢰도, 모델 버전과 근거 미디어 ID를 보존한다.
- 기존 클래스 ID `0`~`11`은 학습 데이터와 모델 출력의 호환성을 위해 변경하거나 재사용하지 않는다.
- 화면과 리포트에는 `균열`처럼 단정하지 않고 `균열로 추정되는 흔적 확인 필요`처럼 표시한다.

### 상태와 규칙

```text
ACTIVE → VIEWED → DISMISSED
ACTIVE ───────────→ DISMISSED
DISMISSED ────────→ VIEWED (복원)
```

- `ACTIVE`: 아직 열람하지 않은 활성 관찰
- `VIEWED`: 사용자가 관찰과 근거를 열람함
- `DISMISSED`: 사용자가 리포트에서 제외함. `하자 아님` 또는 오탐 확정 판정이 아님
- 사용자의 상태 변경은 AI 원본을 변경하지 않고 검토 상태만 변경한다.
- `DISMISSED`는 기본 리포트 수와 본문에서 제외한다.
- 사용자는 `DISMISSED` 관찰을 복원할 수 있으며 복원하면 이미 확인한 상태인 `VIEWED`로 돌아간다.
- 제외·복원 시각과 사용자를 기록한다. 제외 사유 enum과 자유 입력은 P1에서 추가할 수 있다.
- 관찰마다 대표 근거 사진을 정확히 한 장 지정한다.
- 근거 사진 하나가 여러 관찰을 뒷받침하는 것은 허용한다.
- 모든 근거는 같은 임장에 속하고 `UPLOADED` 상태이며 삭제되지 않은 JPEG여야 한다.
- 근거가 보관 정책에 따라 삭제돼도 관찰 원본과 연결 기록은 유지하고 `근거 사진 사용 불가`로 표시한다.
- 관찰 0건은 `하자 없음`이 아니라 `현재 촬영 근거에서 확인 필요 관찰이 생성되지 않음`으로 표현한다.
- 원시 탐지 신뢰도와 관찰 생성 당시 적용한 임계값을 함께 추적할 수 있어야 한다. `confidence`는 확률 보증이나 위험 점수가 아니다.

### 결정 필요

- `OTHER_CHECK_NEEDED`의 사용자 표시 설명과 AI 자유 텍스트 허용 범위
- `DISMISSED` 제외 사유 enum과 선택 입력 범위
- 사용자 직접 관찰 추가 기능 여부

## 13. 방문 전 안심 가이드 `SafetyGuide`

- 사용자가 방문 전에 확인 방법을 학습하는 읽기 전용 콘텐츠다.
- 구역 이름은 공유할 수 있지만 임장·미디어·분석·관찰·리포트와 연결하지 않는다.
- 현장 체크리스트나 완료율을 만들지 않는다.
- 가이드 열람은 분석 완료나 리포트 생성 조건이 아니다.
- `28개 항목`이 남더라도 학습 콘텐츠 수이며 현장 완료 수가 아니다.
- 전문 진단·안전 보증·법률 자문으로 오인되지 않도록 한다.
- MVP에서는 Android 앱에 버전이 있는 정적 콘텐츠로 포함하고 사용자가 건너뛸 수 있게 한다.
- 마지막으로 확인한 콘텐츠 버전은 Android 로컬에만 저장하며 서버 열람 이력이나 완료율을 만들지 않는다.
- 서버 제공 콘텐츠, 게시 기간과 서버 열람 이력은 MVP 이후에 검토한다.

### 결정 필요

- MVP에 포함할 촬영 목적·AI 한계·미디어 보관 안내의 최종 문구

## 14. 사용자 메모 `UserMemo`

- MVP 사용자 메모는 텍스트만 지원하며 임장 전체 또는 선택한 구역에 연결한다.
- 메모는 AI 관찰이 아니며 신뢰도나 모델 버전을 갖지 않는다.
- 사용자 작성 내용은 화면과 리포트에서 `내 메모`로 표시해 AI 설명과 구분한다.
- 음성·STT는 후순위다. 도입할 때는 원본 음성, STT 초안과 사용자 확인 최종 문장을 분리하고 리포트에는 사용자 확인 문장만 사용한다.
- STT 결과는 관찰 유형·구역·검토 상태를 자동 변경하지 않는다.

### 결정 필요

- 텍스트 메모 최대 길이, 수정·삭제 정책과 구체적인 API
- MVP 이후 STT 제공자, 동의 방식과 원본 음성 보관 기간

## 15. 리포트 `Report`

```text
NOT_REQUESTED → WAITING_FOR_ANALYSIS → GENERATING → COMPLETED
                                      ├──────────→ PARTIAL_COMPLETED
                                      └──────────→ FAILED
```

- 매물, 임장, 구역별 분석 상태, `DISMISSED`되지 않은 관찰, 근거 미디어와 사용자 메모로 생성한다.
- 세션이 `ENDED`이고 `mediaFinalizedAt`이 존재하며 모든 미디어 분석이 성공 또는 최종 실패 상태가 되면 서버가 리포트를 자동 생성한다.
- MVP 리포트는 자유 생성 LLM이 아니라 버전이 있는 규칙·문장 템플릿으로 만든다.
- 성공 분석 미디어가 하나 이상이고 최종 실패가 없으면 `COMPLETED`다.
- 성공 분석 미디어가 하나 이상이고 일부가 최종 실패했으면 `PARTIAL_COMPLETED`다.
- 성공 분석 미디어가 하나도 없으면 `FAILED`이며 `NO_ANALYZABLE_MEDIA` 사유를 제공한다.
- 성공 분석에서 관찰이 0건인 경우도 `COMPLETED`이며 하자 없음이나 안전함으로 표현하지 않는다.
- 일부 구역 실패로 완료된 관찰과 근거를 버리지 않는다.
- `PARTIAL_COMPLETED`에는 실패 미디어 수, 실패가 연결된 구역과 미분류 실패 수를 표시한다.
- 모든 관찰 문장은 하나 이상의 근거 `mediaId`로 추적할 수 있어야 한다.
- 사용자 메모와 AI 설명을 구분한다.
- `이 집은 하자가 4개 있습니다`, `계약을 추천합니다` 같은 표현을 금지한다.
- `계약 전 다시 확인해 볼 관찰 결과가 4건 있어요`처럼 표현한다.
- 근거 삭제 시 사용 불가 상태를 표시하고 만료 URL을 재사용하지 않는다.
- 성공 분석에서 관찰이 0건이면 `현재 촬영 근거에서 확인 필요 관찰이 생성되지 않았습니다.`라는 비확정 문구를 사용한다.
- Android는 임장 리포트 조회 API로 생성 상태와 상세를 조회하며 클라이언트에서 리포트 결과를 자체 생성하지 않는다.

### 결정 필요

- 사용자 편집·확정본 개념
- 공유 링크 인증·만료·마스킹·철회
- 실패 미디어 재시도 후 리포트 갱신·재생성 방식

## 16. 푸시 알림 `Notification`

- MVP는 앱 내부 상태 조회와 새로고침을 기본으로 하며 푸시 알림은 필수 기능에 포함하지 않는다.
- 푸시를 도입할 때는 `INSPECTION_ANALYSIS_COMPLETED`, `REPORT_COMPLETED`처럼 전체 작업의 최종 완료만 알린다.
- 부분 완료는 기본적으로 푸시하지 않고 앱에서 실패 미디어와 재시도 상태를 확인하게 한다.
- 알림 권한과 서비스 알림에 동의한 기기에만 보낸다.
- 주소·연락처·구체적인 하자 추정 같은 민감 정보를 본문에 넣지 않는다.
- 앱 이동에 필요한 최소 ID만 사용한다.
- 이벤트 ID로 중복 발송을 방지한다.
- 푸시 실패가 분석·리포트 완료 상태를 실패로 되돌리지 않는다.

### 결정 필요

- 푸시 토큰 API, 다중 기기와 만료 토큰 삭제 정책

구역별 업로드·분석 상태, 관찰 수, 실패 미디어 재시도와 근거 확인 흐름으로 교체한다. 방문 전 안심 가이드는 유지한다.

## 19. 우선 결정할 보완 항목

### 이번 결정으로 확정한 MVP 방향

| 항목 | 확정 방향 |
|---|---|
| 세션 상태 | 서버는 `IN_PROGRESS → ENDED` 또는 `CANCELLED`를 사용하고 보관은 `archivedAt`으로 분리 |
| 분석 집계 | Android 입력값이 아니라 서버가 미디어 원본 상태에서 계산 |
| 업로드 | `clientMediaId`와 `Idempotency-Key`로 중복 방지, 같은 미디어를 최대 3회 자동 재시도 |
| 업로드 HTTP | 요청당 1~20장, 서명 URL 15분, 등록·완료·재시도·목록·상세 API, 멱등성 충돌은 `409 IDEMPOTENCY_KEY_CONFLICT` |
| 영상·JPG | 촬영 후 영상 선택·3초 간격 JPEG 추출을 보장 경로로 사용, 촬영 중 JPG는 실기기 검증 후 선택 활성화 |
| JPEG | 품질 `90 → 85 → 80` 조정 후 필요할 때만 픽셀 축소, 서버 최대 2MiB 유지 |
| 관찰 근거 | 관찰당 1~3장, 대표 근거 1장, 같은 임장의 업로드 완료 JPEG만 연결 |
| 관찰 생성 | classId 기준 13개 `ObservationType` 1:1 변환, 라벨별 버전 설정 임계값 적용, 원시 탐지는 별도 보존 |
| 관찰 병합 | 같은 임장·구역·유형, 6초 이내, crop 유사도 기준을 모두 만족할 때만 병합. 유사도 미구현 시 병합 안 함 |
| 구역 | AI API 결과를 원본으로 보존하고 불확실·실패·미지원은 `UNKNOWN`, 사용자 보정값은 화면·리포트에서 우선 |
| 미디어 확정 | `expectedMediaCount`와 `Idempotency-Key`로 finalize하고 이후 신규 등록은 409로 차단 |
| 리포트 | 미디어 확정과 모든 분석 종결 후 규칙 기반으로 자동 생성하고 성공·실패 수에 따라 `COMPLETED`, `PARTIAL_COMPLETED`, `FAILED` 결정 |
| 관찰 제외 | `DISMISSED` 제외·복원을 지원하고 복원 시 `VIEWED`, AI 원본은 유지 |
| 미디어 보관 | 실패·미완료 24시간, 관찰 없는 자동 사진 7일, 근거·중요 사진 30일, 삭제 요청 후 최대 7일 |
| 메모·알림·가이드 | 텍스트 메모 우선, STT·푸시는 후순위, 가이드는 Android 정적 콘텐츠로 제공 |

## 20. 계약과 구현 반영 순서

1. P0 항목을 제품·Android·서버·AI 담당자가 합의한다.
2. 합의된 규칙만 `team/00_shared/공통 api 계약.md`에 반영하고 미확정 요청·응답은 명시적으로 제외한다.
3. 같은 변경에서 `server/shared-types/openapi/openapi.yaml`을 수정한다.
4. 기존 체크리스트 API·타입은 영향도를 검토해 제거하고, 실제 소비자가 확인되면 별도의 호환성 계획을 세운다.
5. OpenAPI 문법 검증과 Kotlin 타입·API 인터페이스 생성을 실행한다.
6. Flyway와 Kotlin 서버 계층을 구현한다.
7. AI Worker 출력 형식을 공통 또는 내부 계약과 일치시킨다.
8. 부분 실패, 구역별 독립 조회, 재시도, 권한, 멱등성과 비확정 표현을 테스트한다.
9. Android를 구역별 진행·관찰·근거 미디어 흐름으로 연결한다.

미확정 항목을 구현에서 먼저 결정하지 않는다. 공통 요청·응답이나 enum을 바꿀 때는 API 계약, OpenAPI, 서버, AI Worker, Android와 테스트를 같은 변경 단위에서 함께 갱신한다.
